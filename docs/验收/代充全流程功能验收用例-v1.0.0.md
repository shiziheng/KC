# 代充全流程功能验收用例 v1.0.0

> 版本：v1.0.0（对应产品版本 `v2.17.0`）
> 范围：**商品代充全流程**（商品上架 → 前台可见 → 下单 → 资金 → 履约 → 兑换 → 订单中心 → 售后），覆盖**直接代充**与**卡密代充**两条线及各类异常/边界场景。
> 被测对象：`server.js`（后端）/ `public/site/index.html`（KC 原生主站前台）/ `public/admin.html`（技术后台）/ `mysql-store.js`（数据层）
> 状态图例：`✅ 已自动化且跑通`（附脚本与结论）· `🟡 已手工验证`· `⏳ 用例已列、待补自动化`
> 补充：v1.1.0 增补 §十三「Session 生命周期 × 账号状态预检」（代充业务领域评审补充，见文末），v1.0.0 主体用例不变。

## 三、分组 C · 直接代充（冻结 → 核销 / 解冻）

### C-1 下单与冻结

| ID | 场景 | 前置 | 步骤 | 预期结果 | 自动化 |
|---|---|---|---|---|---|
| C1 | 单账号下单 → 金额**冻结** | 余额 ≥ 单价 | 向导走完 ③ 提交 1 段合法 Session → ④ 确认支付 | 下单 200；返回 `status=created` + 内部卡密；**可用余额 ↓、冻结额 ↑（等额）**；订单 `fulfill_mode=direct`/`hold_cents=amount`/`status=created`；钱包流水 `hold` | ✅ `_v2170` F1.1~F1.4 |
| C2 | 余额不足 → 拒绝下单、不建单 | 余额 < 应付额 | ④ 步确认支付 | 402 `INSUFFICIENT_BALANCE`；账单显示「还差 $X」+ 立即充值；**不产生订单、不冻结** | ✅ `_v2160`（第④步余额不足拦截） |
| C3 | 账单展示价 = 结算价 | — | 对比 ④ 步账单「应付总额」与 DB 实扣 | 逐分一致（预览与下单共用 `tenantBatchPlan`） | ✅ `_v2160` F5.5 |
| C4 | 批量：一次粘 N 段 Session → 逐账号一单 | 余额覆盖 N 个账号 | ③ 步粘贴多段 → ④ 确认 | 每账号**独立一单**、各自冻结各自金额；共 N 个 `hold` 流水 | ✅ `_v2160` F5.4、`_v2170` F1 |
| C5 | Session 无效/重复 → 拦截 | — | ③ 步粘贴非法 JSON / 重复邮箱 | 无效行标红并给可执行指引；重复同邮箱**自动去重**；未勾选有效账号时禁止继续 | ✅ `_v2160`（第③步解析与去重） |
| C6 | 不合法 Session 禁止下单 | — | ③ 步粘贴非法内容后强行继续 | 提示后停留在解析页，不进入支付、不建单 | ✅ `_v2163`/`_v2160` 前置断言 |
| C7 | 数量上限与清单操作 | — | 一次粘 >100 段 / 勾选/删除/全选/清空 | 超出 100 的部分标红「一次最多 100 个」；勾选、行内删除、全选可办理、清空清单均生效 | ✅ `_v2160`（第③步清单操作） |
| C8 | Session 不落库 | — | 下单后查 DB 与浏览器存储 | `kc_api_orders`/`task_logs` 无 Session 明文；`localStorage`/`sessionStorage` 无 Session | ✅ `_v2150`/红线（`session_never_persisted`） |

| ID | 场景 | 前置 | 步骤 | 预期结果 | 自动化 |
|---|---|---|---|---|---|
| C9 | 上游成功 → **冻结转扣款** | 已冻结单 | 前端自动发起 `POST /api/run-process`，等待终态 | 任务终态 `success`；订单 `delivered`、`hold_cents=0`、冻结额归零；**可用余额不再变化**；流水 `capture`(change=0) | ✅ `_v2170` F2.1~F2.2 |
| C10 | 开通进度可见（WS） | 同 C9 | 观察 ⑤ 步 | 逐账号状态从「排队中 → 开通中 x% → 已开通」；进度条与汇总同步 | ✅ `_v2160` U5、`_v2150` |
| C11 | 批量部分成功 | 3 个账号，其中 1 个失败 | 走完批量流程 | 成功账号 `delivered`（已扣款）；失败账号 `failed`（已解冻）；**部分失败不回滚整批** | ✅ `_v2160` F5.3/F5.7 |
| C12 | 核销幂等（重复结算不重复加减） | 已 `delivered` 的单 | 再次触发结算 / 重复扫描 | `affectedRows=0` 跳过；`capture` 流水不重复、余额不重复变动 | ✅ `_v2170` F5（幂等口径）、`_v2163` |

### C-3 上游失败 → 解冻

| ID | 场景 | 前置 | 步骤 | 预期结果 | 自动化 |
|---|---|---|---|---|---|
| C13 | 上游失败 → **冻结解冻回可用余额** | 已冻结单，上游判定失败 | 等待任务终态 / 周期对账 | 订单 `failed`、`hold_cents=0`、冻结归零、**可用余额回补 +amount**；流水 `release`(+amount)；`fail_reason` 留痕 | ✅ `_v2170` F3 |
| C14 | 失败后前端口径 | 同 C13 | 打开「我的订单」 | 徽标「失败（已解冻）」；副标题「订单未成功（冻结金额已解冻）」；时间线末节点「已解冻 · 冻结金额已退回你的可用余额」 | ✅ `_v2170` U3/U4、代码口径 |
| C15 | 解冻幂等 | 已 `failed` 的单 | 重复扫描对账 | 不再重复加钱（闸门 `status='created' AND hold_cents>0`） | ✅ `_v2170` F3（闸门） |
| C16 | 开通任务长时间无进展 → 解冻 | 任务 `running` 且超 15 分钟未更新 | 等待对账 | 订单 `failed` + 解冻（`ACTIVATION_REFUND_TASK_TIMEOUT_MS`，默认 15 分钟） | ⏳ 与 C13 同路径，阈值场景待补 |
| C17 | **未启动开通 → 超时自动解冻** | 下单后**从未**发起开通 | 等待（下单后约 30~35 分钟） | 订单 `failed`、`fail_reason='未启动开通，超时已解冻'`、可用余额回补；**资金不长期挂起** | ⏳ `_v2170` F3 以「构造 failed 任务 + 对账」验证同路径；纯超时场景待补（可用 `ACTIVATION_HOLD_UNSTARTED_TIMEOUT_MS` 调小实测） |
| C18 | `manual`/`maintenance` → **保持冻结**（不自动解冻） | 任务进入人工/维护态 | 等待对账 | 订单仍 `created`、`hold_cents>0`（冻结保留待人工）；前端显示「需人工处理，请联系客服」 | ⏳ |
| C19 | 未启动单可**手动补开通** | direct 单 `status=created` 且任务 `none` | 订单详情点「继续开通」 | 进入兑换向导并预填该内部卡密；补启动成功后转 capture | ✅ `_v2163` F8（同路径）、`_v2170`（口径） |

### 13.8 拦截与提示交互设计（落地设计 + 新增用例）

**核心原则：拦截按「行（账号）粒度」，不整批阻断。**
回答「是否 Session 解析后不允许选择」——是**逐行**不允许，而非整批：批量场景下仅剔除问题账号、其余照常结算；只有**全部行均被拦截**时才禁用「下一步」。实现路径为「解析 → 自动预检 → 逐行状态 → 逐行勾选控制」，并在服务端做兜底复检。

**每行账号在第 ③ 步内的状态机**

| 阶段 | 触发 | 该行表现 | 可否勾选 |
|---|---|---|---|
| ① 解析 | 粘贴 Session | 前端本地切分 / 格式校验 / 去重 / 邮箱脱敏回显（现有能力） | 格式有效者可勾（待预检） |
| ② 预检 | 解析完成后**自动并发**调 `POST /api/public/subscription/check` | 逐行显示「正在校验账号状态…」（loading）；「下一步」禁用 | — |
| ③ 判定 | 预检返回 | 逐行落定最终态（见判定矩阵） | 见矩阵 |
| ④ 汇总 | 全部返回 | 「共 N 个 · M 个可办理 · 已剔除 X 个」+「仅选可办理」；「下一步」启用 | — |

**判定与交互矩阵（D1~D4 定稿口径）**

| 预检结果 | 决策 | 可勾选 | 徽标 | 行内提示 / 用户动作 |
|---|---|---|---|---|
| 无订阅、未付费 | — | ✅ 可勾（默认勾选） | ✅ 可办理 | — |
| 订阅已到期 / 已取消 | — | ✅ 可勾 | ♻️ 可续费 | 「该账号订阅已于 {date} 到期，可重新开通」 |
| **已开通 Plus 且有效期内** | D1 拦截 | ⛔ **不可勾**（`disabled` + 置灰） | ⛔ 已开通·无需重复开通 | 「Plus 有效期至 {date}（剩余 N 天）」；出口「换其他账号 / 联系客服」 |
| 已是 Pro | D1 拦截 | ⛔ 不可勾 | ⛔ 已是 Pro | 「该账号已是 Pro，无法开通 Plus」 |
| Team / 企业席位 | D1 拦截 | ⛔ 不可勾 | ⛔ 团队账号 | 「该账号属于团队账号，无法单独开通」 |
| 订阅来自 App Store / Google Play | D2 提示冲突 | ⚠️ **默认不勾；确认后可勾** | ⚠️ 渠道冲突 | 「该订阅由 App Store 管理，续费请前往 App Store」+「仍要通过本平台开通」→ 二次确认弹层 |
| 凭证 `exp` 已过 | 阻断 | ⛔ 不可勾 | ⛔ Session 已过期 | 「重新获取 Session」三步图文 |
| 预检不可达（超时 / 5xx） | D3 不处理 | ✅ 可勾（放行） | ⚠️ 待复核 | 「状态校验暂不可用，将按可开通处理」 |
| 邮箱 ≠ 平台顾客邮箱 | D4 放行 | ✅ 可勾 | — | 脱敏回显 `a***@gmail.com` |

**交互细节（落地实现须逐条满足）**

1. **自动预检**：解析完成后**无需用户点击**即自动并发校验；期间「下一步」`disabled` 且显示「正在校验账号状态…」（含超时兜底文案）。
2. **拦截行非静默**：`checkbox` 置 `disabled` + `aria-disabled`，整行置灰；用户点击拦截行须弹出说明（tooltip / toast），**不得静默无反应**。
3. **全选 / 清空语义**：全选**仅选中「可办理」行**、跳过拦截行；清空清零；提供「仅选可办理」一键操作。
4. **汇总与放行**：账单仅结算已勾选的可办理行；若可办理数 M=0 → 「下一步」`disabled` + 「没有可开通的账号，请检查 Session 或联系客服」。
5. **D2 二次确认门槛**：渠道冲突行勾选前必经确认弹层（「该账号订阅由 App Store 管理，确认仍要通过本平台开通？」），确认后该行转为可结算。
6. **后端兜底（K11）**：服务端**建单前独立复检**、不信任前端预检；命中拦截 → 该账号 422 `ACCOUNT_ALREADY_SUBSCRIBED` 且**不冻结**；批量中该行失败不影响其余（对齐 C11 部分失败不回滚整批）。

**新增验收用例（交互落地）**
