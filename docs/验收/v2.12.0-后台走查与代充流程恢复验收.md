### 1.3 走查发现并修复的 3 个真实缺陷（本版核心价值）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| **D1** | **创建商品必失败**：`POST /api/admin/products/save` → **500 `Data truncated for column 'kc_type'`** | 新建商品分支写入 `kc_type='subscription'`，而 `kc_plans.kc_type` ENUM 只有 `recharge/account/entitlement`（且项目约定 R2 阶段统一 `recharge`，见 `tools/migrate-pricing.js`） | `server.js` 改用既有归一函数 `planTypeNorm(b.kc_type)`（默认 `recharge`） |
| **D2** | **权益包保存「提示已保存但服务端 400 / 无动作」**：`POST /api/admin/entitlements/rules` → 400「code 必填」 | `public/admin.html` 的 `authFetch()` **从不设置 `Content-Type`**：字符串 body 被浏览器按 `text/plain` 发送 → 服务端 `express.json()` 跳过解析 → `req.body = {}`。凡「传 JSON 但未显式带 header」的调用全部中招（权益规则新建/启停等） | `authFetch` 在「字符串 body 且调用方未指定 Content-Type」时兜底补 `application/json`（FormData/Blob 不受影响）；**一处修复覆盖全部同类调用** |
| **D3** | **权益页规则列表恒显示「暂无规则」**（用户持有权益查询、权益明细同病） | `loadEntitlementsList` / `_entResolveUserId` / `loadEntitlementGrants` 把 `authFetch()` 返回的 **Response 当作数据**读 `r.data` → 恒 `undefined` | 三处改为 `await res.json()` 后再取 `data` |

> 这三个缺陷均为**真实用户可见故障**（不是测试脚本问题）：D1 让「新建商品」完全不可用；D2 让「新建权益规则 / 启停」静默失败；D3 让权益页看不到任何规则。均由本次逐菜单走查发现，属用户要求「确保功能可用，没有报错」的直接产出。

## 二、任务 2 · 前台展示方案（配色 / 内容布局 / 可行性判断）

产出：**`docs/方案/前台展示方案-v1.0.0.md`**（含参考站实测拆解、可落地 token、布局规格、组件规范、验收口径）。

参考站实测（`logs/ref-ezsub/*.png`）：底色 `#0D0E12`、强调色 `#76B900`（亮柠绿）、卡片 `rgba(20,24,22,.7)` + `1px #1E2A1E` + `16px` 圆角、Hero 双行标题（第二行用强调色）+ 单发光 CTA 卡、信任条（logo 墙 + 3 指标）、3 能力卡、FAQ 手风琴、三列页脚。

**独立体验判断（不附和）**：

- **可用且推荐借鉴**：标题靠「颜色」分级、首屏唯一主 CTA、卡片统一描边代替阴影、FAQ 收页。
- **明确不照搬**：① **客户 logo 墙**（我们是单点代充工具，借别家 logo 背书会被误解为代理关系，且涉嫌品牌误用）→ 替换为「已交付订单数 / 平均开通时长 / 到账率」类**可核验自证指标**；② **大数字指标**（量级不支持，编数字反噬信任）；③ 绿色地球/粒子大背景（体量大、移动端耗电）；④ Cookie 弹窗与语言/币种切换（我们没有多语言多币种，加了就是假功能）；⑤ **全站通体深色 + 高发光**：发光不得用于金额/地址/二维码面板（深色下须用高对比白字 + 低饱和描边）。
- **落地方式**：`public/site/index.html` 单文件内换 token + 首页区块重排 + FAQ 改手风琴；**深色建议作默认，但保留浅色用于收银/充值强光可读**；租户品牌色注入优先级最高（不破坏白标）。
- **风险**：亮绿与租户品牌色冲突；「信任条」必须真实数据否则反噬。**建议分两步落地**（先 token + 首页重排 → 再评估信任条与深色默认化）。

## 三、任务 3 · 代充「购买 → 输入并校验 Session → 开通」流程恢复

### 3.1 丢失原因（定位结论）

- **能力没丢**：后端 `/api/verify-cdk`、`/api/run-process`（`handleActivationRequest` 读 `req.body.session`）与上游 ZovoCard（`gptApi.inspectPay/submitPay`）**均在位**。
- **丢的是「购买流程里的 Session 环节」**：v2.0.0/v2.1.0 Xboard 退场时，旧的「代充向导（登录官网 → 取授权信息 → 粘贴解析 → 付款开通）」随主题注入退场消失；KC 原生前台改成了**两段式**——下单只交付**一张卡密**，Session 环节被挪到独立的「兑换卡密」页，且下单成功后**没有任何引导**指向那里（订单详情里卡密也只是纯文本，无入口）。用户感受到的「这套流程没有了」即此。

### 3.2 恢复方案（对齐旧「粘贴 → 校验 → 付款开通」顺序）

在 `public/site/index.html` 落地：

1. **代充商品详情页**：新增流程提示（① 下单 ② 获得卡密 ③ 粘贴 Session 开通），并显式声明「不需要账号密码、Session 不落库」；按钮文案改「**购买并去开通**」。
2. **下单前先收 Session**：代充商品**必须**粘贴 Session 并**本地结构校验通过**（`rdCheckSession`：JWT 头/签发方/aud/账号信息/`model.request`/有效期）才允许下单 —— 避免为无效账号付款。
3. **下单成功即闭环**：返回卡密后自动进入兑卡视图、预填卡密与已校验 Session，并**自动提交开通**（复用既有 `/api/run-process` + WebSocket 进度面板）；不自动提交的场景（如从订单详情进入）保留手动「开始开通」。
4. **我的订单 → 订单详情**：卡密旁新增「**去开通**」按钮（跳兑卡并预填卡密）。
5. **Session 铁律**：仅存浏览器内存（`state.pendingSession`），**不写 localStorage/sessionStorage、不落库**，与红线「用户授权信息不保存」一致。
