## 0. 一页结论

1. 系统乱的根源不是组件多，而是**没有唯一主路径**：Xboard 主链路与"独立代充系统"两条轨道并行、四套后台职责交叠、Mock / 真实两套语义并存。
2. 重整方向：**一引擎 + 一商城 + 一通道** —— KC 做引擎（上游接入 / 自动代充 / 发卡），Xboard 做业务前台（用户 / 订单 / 收款 / 余额），BEpusdt 做收款通道；独立前台 / 独立后台**冻结**，上线稳定后再评估去留。
3. ⛔ **先修一个断点**：KC 侧对外集成接口在 10-07 恢复时被整体回滚丢失（运行实测 404）。完整实现已找回并固化（见第 2 节 F1），修复 = 合并 + 跑现成验收脚本，**不需要重新设计**。
4. ⚠️ **先做一件事**：v1.9–v1.11 全部改动（约 40 个文件）至今未提交 —— 阶段 0 第一件事就是固化提交，杜绝再次不可逆丢失。
5. 上线最短路径：**修断点 → 你提供真实钱包地址 → 上游只读验通 → 一笔小额真实首单 → 补偿 / 对账 / 监控 / 手册到位 → 小流量试运营**。其余全部不做。

## 3. 目标架构：一引擎 + 一商城 + 一通道

**低耦合不等于拆成很多服务，而是：单一职责 + 窄契约 + 单一主路径。**

```text
用户（注册 / 充值 / 下单 / 售后）
        │
        ▼
① Xboard 业务前台（业务正本：用户、订单、余额、收款入口）
        │                     │
        │                     └── 收款契约 → ③ BEpusdt（USDT 收单：易支付 submit.php + 回调）
        │
        └── 履约契约（唯一通道）→ ② KC 代充引擎
                                      │  POST / GET /api/integration/cdk/issue（幂等发卡 / 回查）
                                      │  GET  /api/integration/task/status（进度与失败原因）
                                      │  GET  /api/integration/health（探活）
                                      ▼
                               上游适配层（同构适配器接口）
                                      ▼
                               ZovoCard（现有）→ 未来第 2 家上游（挂起）
```

**职责边界与数据正本：**

| 组件 | 唯一职责 | 数据正本 | 禁止事项 |
|---|---|---|---|
| ② KC 引擎 | 上游接入、代充任务编排与重试、CDK 发放、任务状态 | `plus_papay`（任务 / 卡密 / 集成记录） | 不拥有用户、不收款、不写 Xboard 业务表 |
| ① Xboard 商城 | 用户、商品、订单、余额、收款入口、售后、分销 | `xboard` 库 | 不直接调用上游、不实现代充逻辑 |
| ③ BEpusdt | USDT 收单与回调 | 自身 SQLite | 不承载业务逻辑 |
| 独立前台 / 后台（`web/`、`business/`） | ——（冻结） | `kc_business`（保留只读） | 不再开发、不接真实流量 |

> 冻结说明：保留代码与数据，停止继续投入；上线稳定后再按第 7 节阶段 4 决定去留。

## 4. 三个契约（冻结 v1，落纸到 `docs/接口/`）

- **C1 履约契约（Xboard → KC）**
  - `POST /api/integration/cdk/issue`：幂等键 = 商城订单号（`ref`）；重复请求返回同一张卡（`reused=true`）。响应 `{success:true,data:{ref,cdk,plan_type,reused}}`。
  - `GET /api/integration/cdk/issue?ref=`：回查。
  - `GET /api/integration/task/status`：开通进度与失败原因（脱敏、截断）。
  - `GET /api/integration/health`：探活（含开关状态）。
  - 鉴权：`X-Integration-Key`（KC 后台生成）。
  - 失败语义：调用端（Xboard 插件）2–3 秒超时且吞异常 → 失败订单必须进入人工 / 补偿队列，**绝不能出现"钱在平台、卡没发出、无人管"的状态**。
- **C2 支付契约（Xboard ↔ BEpusdt）**：易支付 `POST /submit.php` + 异步回调；充值成功 → Xboard 余额。**真实钱包地址是当前唯一硬阻塞。**
- **C3 上游适配器契约（KC ↔ 上游）**：已存在的同构接口（`testConnection / fetchPlans / inspectPay / submitPay / queryOrder / queryTask / queryBalance`）——新增第 2 家上游 = 写一个同构 client + 套餐路由规则，**不动其他任何组件**。当前 `zovocard-client.js` 是第一实现；`REQUIRE_ZOVOCARD_MOCK` 安全锁在批准验证前不得解除。

## 6. 上线缺口清单（P0 无它不能收钱 / P1 上线后一周内）

**P0：**

1. **F1 修复**：集成接口合并回当前版本；三个验收脚本全绿（含并发只发 1 张）。
2. **F2 固化**：全部未提交改动提交归档。
3. **真实收款钱包地址**（你提供，建议 TRC20）→ BEpusdt 绑定 → 建 1 USDT 测试单验证收银台 → Xboard 配好 epay 渠道。
4. **上游只读验通**：解除 Mock 锁前先只读 `testConnection / fetchPlans`（确认密钥 / 代理 / 白名单），再另行批准。
5. **一笔小额真实首单**：充值 → 余额 → 下单 → 发卡 → 代充 → completed → 用户可见进度与回执；对账一次（订单 / 任务 / 上游三方）。
6. **失败兜底路径验收**：履约失败 → 用户可见失败原因 → 人工 / 自动补偿（Xboard 售后 + `KcCompensation` 已有基础，验证贯通）。

**P1：**

7. 监控告警：容器健康、任务失败率、上游余额（`spendable_balance`）、订单积压（Telegram 通知已有基础）。
8. 运维手册一页纸：重启 / 补单 / 退款 / 换 key / 回滚 + 四个后台各自管什么。
9. 运营物料：Session 获取指引、售后话术。
10. 文档补齐：`docs/接口/`（C1 / C2 / C3 契约）、`docs/设计/`、`docs/01_目录结构.md`。
