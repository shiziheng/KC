## 三、跨批次的关键口径（先钉死，避免返工）

1. **租户作用域铁律**：一切租户接口取 `req.tenant.id`，**禁止从请求体读 `client_id`**（[开发规范/多租户铁律]）；代理商侧响应**必须剔除 `cost_cents`**。
2. **权益双维度不串账**：顾客维度口径是 `kc_entitlement_grants.customer_id`（[mysql-store.js#L763 附近引用]），**不是** `user_id`；现有 `/api/admin/entitlements/user-lookup` 按 `user_id`，在批次 1 降级为"跳转入口"（方案 §九 去重决策 3）。
3. **两个"日志"不许混**：现有「运行日志/登录日志」= 系统/任务日志；新增「操作审计」= 谁改了什么（`kc_audit_logs`）。
4. **「账单记录」改名**：平台侧开通账单 → 建议改名「**开通账单**」（方案 §九 决策 1）；顾客钱包账单只出现在「顾客详情 → 账单」，**不设顶级菜单**（决策 2）。
5. **金额口径**：一律"分→`$`"展示；「原价」来自 `v2_plan.prices`（美元）×100，勿与 `price_cents` 混用；权益订单呈现**双价**（`kc_entitlement_uses.original_cents / final_cents / discount_cents`，[server.js#L6671](file:///d:/tools/KC-PAY-GPT/server.js#L6671)）。
6. **菜单铁律（现有）**：技术后台导航当前为硬编码 5 组内平铺；本方案新增项**归组**，不无限加顶级项（方案 §十 目标 IA 即批次 4 的种子数据）。

## 四、批次 1 · v2.3.0 顾客管理域（P0，工作量最大）

**交付**：技术后台 + 代理商后台可"**看全一个顾客**"（只读四视图）并执行最低限度的资金安全写操作（冻结/解冻）。

### 4.1 数据层（mysql-store.js）
- 新增 `ALTER TABLE kc_api_orders ADD COLUMN biz_type ENUM('topup','account','website','entitlement','other') NOT NULL DEFAULT 'other' AFTER source`；
  - 历史回填：按 `sku_code` join 商品目录 `category` 一次性 UPDATE（映射 `recharge→topup / account→account / website→website / pack→entitlement / 其余→other`）。
  - **单一事实源**：把 `categoryKeyNorm`（[server.js#L5842](file:///d:/tools/KC-PAY-GPT/server.js#L5842)）抽成前端/目录/订单共用 key，消除两套映射漂移。
- 扩枚举：`ALTER TABLE kc_customer_wallet_ledger MODIFY type ENUM('recharge','consume','refund','adjust') NOT NULL`。
- 顾客强制首改位：`ALTER TABLE kc_customers ADD COLUMN must_change_password TINYINT(1) NOT NULL DEFAULT 0`（供批次 1 临时密码 + 批次 3 令牌共用）。

### 4.2 后端 API（server.js，全部挂 `authenticateAdmin`）
| 端点 | 说明 |
|---|---|
| `GET /api/admin/customers` | 分页 + 搜索（邮箱/昵称）+ 筛选（租户 / status） |
| `GET /api/admin/customers/:id` | 概览聚合（余额 + 订单数 + 权益数 + 充值合计） |
| `GET /api/admin/customers/:id/wallet` | `ledger[]`（链式自洽）+ `recharges[]` + `summary{recharge_total,consume_total,refund_total,balance}` |
| `GET /api/admin/customers/:id/orders?biz_type=&status=&source=&page=` | 并**两源**：`kc_api_orders` + `kc_customer_pack_purchases` |
| `GET /api/admin/customers/:id/entitlements` | 按 `customer_id` 命中（**不按 `user_id`**） |
| `POST /api/admin/customers/:id/status` | 冻结/解冻（`active` ↔ `disabled`） |
| `POST /api/admin/customers/:id/note` | 备注/昵称 |
| `POST /api/admin/customers/:id/reset-password` | **批次 1 最小版**：生成一次性临时密码（仅展示一次）+ 置 `must_change_password=1`；批次 3 内部改走 `kc_password_resets` 令牌（端点契约不变） |
| `POST /api/admin/customers` | 手动开号（同租户 email 唯一） |
| `GET/POST /api/tenant-admin/customers*` | 代理商镜像，作用域锁 `req.tenant.id`、**剔除 `cost_cents`**、越权返空/403 |

### 4.3 前端
- `public/admin.html`：新页「顾客管理」，归入**新组「业务运营」**；详情用抽屉 + 多 tab（概览 / 权益 / 订单 / 账单），表格 375px 可横滚。
- `public/tenant-admin.html`：镜像只读 + 冻结/改密，作用域收窄。

### 4.4 退出条件
- 功能：TC-F-01~06、08（含 `balance == balance_cents` 一致、订单按 `customer_id` 计数一致、权益按 `customer_id` 命中、代理商无 `cost_cents`、越权 403）。
- UX：TC-U-01、03、05（loading/空态、金额全 `$`、危险操作二次确认显示余额与未完成订单数）。
- 门禁：三绿 + 五件套同步。

## 六、批次 3 · v2.5.0 密码与账号安全 + 操作审计（P0/P1）

### 6.1 数据层
- 新表 `kc_password_resets`（`token_hash` / `account_type` / `account_id` / `expires_at` / `used_at` / `created_by`；**存 hash 不存明文**，30 分钟过期，用后即焚）。
- 新表 `kc_audit_logs`（`actor_type/actor_id/actor_email/action/target_type/target_id/before_json/after_json/ip/created_at`）。

### 6.2 实现
- **四场景统一抽象**（方案 F2）：A 平台 super 重置管理员；B 租户 owner 重置 staff；C 管理员重置顾客；D 顾客自助找回（前台，属另一批，本期仅留接口位）。
- 批次 1/2 已交付的"临时密码"端点，本批次**内部改走令牌表**（契约不变）。
- 写操作审计中间件：改价 / 发权益 / 删卡 / 冻解 / 改账号 → 自动落 `kc_audit_logs`。
- 登录安全：会话超时与强制下线、密码强度、强制首改、2FA 下放租户 owner。

### 6.3 退出条件
TC-F-07、12、14、15（四场景各能重置；令牌二次使用失败且 30min 过期；重置后强制改密；审计四要素齐备）。

> **对方案 §六 顺序的依赖修复建议**：审计表(`kc_audit_logs`)按方案排在批次 3，但批次 1 的「冻结/改密」与批次 2 的「改账号/角色」**都属于高危写操作**，方案 §七/TC-F-12 也要求审计。若严格照原序，前两批的写操作会**先无审计、后补**。建议把 `kc_audit_logs` 表 + 极简 `audit()` 落库助手**前移到批次 1**，批次 3 只做"四场景 + 覆盖面铺满"。此为**顺序微调，不改方案范围**。
