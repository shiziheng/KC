## 0. 一页结论

1. "重建 vs 改"是伪二选一：先把"后台"**拆成两层**，两层分别决策——
   - **交易内核维护层**（用户 / 订单 / 余额 / 支付 / 分销）：Xboard 原生域，成熟、可用、在跑 → **继续借壳，但"少改、收敛"**；
   - **代充业务运营层**（商品 / 卡密 / 任务 / 上游 / 补偿 / 对账）：业务正主是我们，Xboard 天生没有 → **自建**。
2. **结论：运营层自建（重建），内核层借壳（改到"少碰"为止）。** 不是二选一，是各归其位。
3. "完全自建并最终替换 Xboard 内核"：**不启动、不关闭**——写入触发条件（§6），由业务数据决定何时立项；不因"后台不好用"启动。
4. 现有资产已为这个结论铺好一半路：插件侧 12 个 admin 接口已部署、Xboard 后台已收敛为 6 个菜单且挂有"代充运营"入口——**缺的只是运营台本体**（`business-admin` 仍是 Mock、已冻结）。

## 1. 问题从哪里来（现状痛点，先对齐事实）

- **四后台各有分工，但没有"一张看板"**：KC 技术后台（引擎/集成）、`business-admin`（Mock 运营台，冻结）、Xboard 后台（运营在用）、BEpusdt（通道）。运营想看懂"今天发生了什么"，要开四个页面。
- **Xboard 后台的机场基因**：管理端是编译产物 SPA；商品表单一半是机场字段（权限组/流量/限速/设备数…）；语义错位（它的"开通"= 开节点+重置流量，我们要"发卡+代充"）。菜单噪音已用壳脚本收敛为 6 项，**字段级噪音仍在**。
- **业务概念的增长全部堆在 Xboard 上**：`v2_plan` 加 3 列（`kc_is_topup` / `kc_topup_amount` / `kc_card`）+ 4 处内核补丁（PlanService / TopupController / OrderService / CheckCommission）+ 插件 7 张表 9 个控制器 + 3 份前台注入。**每加一个业务概念 = 再动一次别人的系统。**
- **结构矛盾**：我们的业务模型在长大，Xboard 的后台界面停在原地——而且它服务的是机场模型，永远长不出代充的界面。

## 3. 三个选项摊开（A 改 / B 全自建 / C 分层）

### A. 继续改 Xboard 后台（延长线）

- 已走过的部分：菜单收敛、插件配置页（config.json 原生渲染）、"代充运营"外链。
- 再往前只有两条极限路线：
  - **A1 壳层 DOM 改造**（在后台页面上隐藏商品表单的机场字段等）：技术可行（菜单收敛已有先例），但每页每块都是**运行时补丁**——Xboard 前端一变就回归；只治界面、治不了语义。
  - **A2 Fork Xboard 源码做定制镜像**：换来干净后台，但从此**接手一个 fork**（构建链、升级合并、补丁永续），团队从"用工具"变成"维护一套别人写的 PHP 面板"。
- 判定：A1 边际收益递减；A2 成本与收益不成比例。**A 适合作为过渡态，不适合作为终局。**

### B. 完全自建（重建后台并最终替换 Xboard）

- 内容不是"写个后台"：是自研 用户 / 订单 / 支付 / 余额账本 / 商品 / 分销 全套 + 数据迁移 + Xboard 退场 = **重做商城**。
- 真正的代价在"账本"：余额是真钱、订单是凭证。迁移与双跑的风险，与"后台不好用"完全不成比例。
- 判定：**不因"后台烦"启动；由触发条件启动（§6）。** 若启动，先按 §7 的试点原则来。

### C. 分层（推荐）：业务运营台自建 + Xboard 保留为交易内核

- **一句话：让"自建运营台"成为日常正主；Xboard 后台退为原生域兜底。**
- 做法（先薄后厚，全部可停）：
  1. **契约先行**：运营台不直连任何一方数据库，全部走契约——
     - KC 侧：`admin/integration/*`、`admin/card-config/*`（F1 合并后）+ 待补的任务/上游只读接口；
     - Xboard 侧：复用插件 `admin/kc/*` 的 12 个接口 + 按需求补 6~10 个（以只读为主：订单查询/用户查询/卡密列表；写操作严格白名单）；
     - 通道侧：BEpusdt 只读对账（复用 MIG-016 思路）。
  2. **运营台 v1（只读聚合）**：今日总览 / 订单流 / 任务流 / 失败与补偿队列 / 上游余额 / 通道对账。技术上挂在 KC app 静态页 + BFF，复用现有栈与 `deploy-manifest` 部署链，不新造大楼。
  3. **写操作逐步接管**：补偿重试/标记（接口已有）→ 卡密 → 商品卡片配置（接口已有）→ 开关与阈值（KC `app_config`）。每接一个，Xboard 后台少开一次。
  4. **商品上架工作台（收尾）**：自建商品配置页（写 `kc_*` + 必要的原生字段，经契约），Xboard 商品页只读化；配套产出《商品上架最小规范》（运营一页纸，可合并 10-09 的 F4 核查内容）。
- **"少改 Xboard"组合红线**（写死，防回退）：Xboard 侧今后只允许三类改动——① 保命豁免补丁（如 kc_is_topup）；② 插件 API；③ 壳层菜单收敛。其余一律进运营台。
- **`business-admin`（Mock）的处理**：不直接解冻。它绑定 Mock 数据层、与真实数据脱节；保留为信息架构参考，运营台按契约新做。

## 4. 综合对比

| 维度 | A 改 Xboard | B 全自建（含替换内核） | C 分层（推荐） |
|---|---|---|---|
| 业务模型契合（代充原生） | ○ 受制于机场模型 | ● 完全原生 | ● 运营层原生，内核借壳 |
| 原生能力复用（用户/订单/余额/支付/分销/工单） | ● 全复用 | ○ 全部重做 | ● 全复用 |
| 升级/重建生存性 | ○ fork/补丁永续 | ● 不适用（已自主） | ● 只碰壳与插件，不碰内核代码 |
| 初始投入 | 小（延续现状） | 大（以月计） | 中（可分阶段） |
| 长期维护成本 | 高（补丁债滚雪球） | 高（自研全栈自立） | 中（自研一层 + 薄契约） |
| 多上游 / 多商品形态扩展 | ○ 天花板锁死 | ● 自由 | ● 运营层自由 |
| 运营体验（单入口看板） | ○ 多后台永远并存 | ● 单系统 | ● 单入口聚合 |
| 资金/账本安全 | ● 账本原地不动 | ○ 迁移风险最大 | ● 账本原地不动，写操作走契约 |
| 可逆性 | ● 随时停 | ○ 推倒重来 | ● 每阶段可停可退 |

## 6. 内核替换（B）的触发条件（写下来，免拍脑袋）

任意满足 **2 条** → 启动"内核替换"立项评估：

1. 日常运营 ≥80% 动作已由运营台承载，且 Xboard 后台周打开次数 < 3；
2. Xboard 连续两次升级/重建破坏补丁，且修复成本 > 在运营台重做同等功能的成本；
3. 业务形态超出 Xboard 表达（多商城 / 多租户 / 复杂定价 / 新商品类型）；
4. 出现"必须改内核数据模型"的刚需（如商品模型彻底重定义）；
5. Xboard 上游停止维护、或出现无法绕开的安全问题。

---

## 7. 若走 B：试点原则（先立规矩）

- 试点模块选"独立性强、资金风险低"：候选 = 商品目录（只读+配置）或 售后工单；
- 账本 / 余额 / 订单：**不试点、不先动**；迁移必须双跑对账 ≥ 1 个结算周期、单独立项、双人复核。
