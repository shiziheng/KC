# 第一部分 · 四项处置方案

## 一、H1 品牌名：定为「KC 直供」，做成后台可配置

### 1.1 决策

品牌名定为 **KC 直供**，且**不硬编码** —— 做成 KC 后台可改的配置项。

### 1.2 为什么要可配置（而不是直接写死）

写死的话，以后每次改品牌名（换名、做第二个站、A/B 测试文案）都要改代码 + 重新部署注入。做成配置后，**改一个输入框、点保存，全站立即生效**。

### 1.3 配置项设计

KC 后台新增一个轻量区块「**站点品牌**」（放在现有设置类页面里，或独立一页）：

| 配置键 | 含义 | 默认值 | 影响位置 |
|---|---|---|---|
| `brand_name` | 品牌名 | **KC 直供** | 顶栏 Logo、抽屉头、页脚、游客页、浏览器标题 |
| `brand_badge` | Logo 徽标文字（方块里那 1–3 个字符） | **KC** | 顶栏左上角方块 |
| `brand_sub` | Logo 旁副标 | **GPT 代充 · 批发价** | 顶栏副标 |
| `brand_slogan` | 宣传定位句 | **一个人也算批发** | 页脚、落地页 |

### 1.4 技术落点（三处，都很小）

```
① 存储：KC 库 app_config
   表结构实测：config_key(varchar64) / config_value(text) / created_at / updated_at
   → 新增 4 行：brand_name / brand_badge / brand_sub / brand_slogan

② 读取：KC 新增公开接口
   GET /api/public/branding        ← 与现有 /api/public/runtime 同风格，无需鉴权
   返回 { brand_name, brand_badge, brand_sub, brand_slogan }
   （KC server.js 现有公开接口：admin-paths / subscription/check / payment-region / runtime）

③ 应用：前台注入脚本启动时拉一次
   - 覆盖 custom_html 里 5 处品牌名（顶栏 Logo / 抽屉头 / 门户页脚 ×2 / 游客落地页）
   - 写入 localStorage 做首帧缓存，避免刷新时"先闪旧名再变新名"

④ 浏览器标题：改 Xboard 的 app_name
   ⚠️ 标题是**服务端渲染**的（实测 8 个页面 title 全是 `XX | KC 加速`），
      注入脚本改不了分享预览（微信/QQ 抓的是原始 HTML）。
   → 保存品牌配置时，**同步写 Xboard 的 v2_settings.app_name**
      KC 已有跨库写入能力（参考 migrate-upstreams.js 写 v2_plan 的先例）
   → 写完必须 docker exec xboard php artisan optimize:clear
```

### 1.5 兜底

接口不可用 / 未登录 / 网络慢 → 一律 fallback 到硬编码默认值（`KC 直供`）。**不允许出现空白或无品牌名的状态。**

### 1.6 落地顺序

1. 先把 `app_name` 与 5 处硬编码统一改成 **KC 直供**（本次见效）
2. 再做后台配置项 + 接口 + 注入读取（下次改名字就不用找开发了）

> 也可以一步到位。但如果想今天就见效，建议按上面两步走。

它不是会员等级，是**预购的低价购买次数**：

**次数用完了怎么办？** 按原价继续买，或者随时补一个新包。

## 三、H4 历史套餐：重点改（但有硬约束）

### 3.1 ⚠️ 先说硬约束：**这些套餐不能删**

我查了订单引用情况：

| 套餐 | 订单引用 |
|---|---|
| #6 余额充值 $2 | **25 笔** |
| #2 余额充值 $14 | **14 笔** |
| #10 余额充值 $7 | 5 笔 |
| #18 余额充值 $100 | 2 笔 |
| #7 / #8 / #9 余额充值 $2 | 各 1 笔 |
| #11 余额充值 $14 | 1 笔 |
| #14 余额充值 $1 | 1 笔 |
| **#12 余额充值 $7** | **0 笔** ← 唯一可删 |

**关键原因**：`v2_order` 表**没有套餐名快照**（实测字段只有 `plan_id`，没有 `plan_name`）。订单页的套餐名是**联表 v2_plan 查出来的** —— 一旦删除 plan 记录，**这些历史订单的商品名会变空或整行消失**。

> 所以「删掉垃圾套餐」这个动作，代价是破坏 50 笔历史订单的显示。**不值得。**

### 3.2 正确做法：归档化（三步）

**第一步 · 删掉唯一零引用的**

```sql
DELETE FROM v2_plan WHERE id = 12;   -- 余额充值 $7，订单 0 笔，无引用风险
```

**第二步 · 其余 10 个统一重命名为「历史档位」**

```sql
UPDATE v2_plan SET name = CONCAT(name, '（历史档位）')
WHERE id IN (2, 6, 7, 8, 9, 10, 11, 14, 18) AND show = 0;
```

重命名后：
- **后台商品列表**：一眼可辨，不会再和现行档位混淆 ✓
- **历史订单页**：显示「余额充值 $2（历史档位）」—— **比现在更清楚**（用户知道这是老订单）
- **前台完全不影响**（`show=0` 本就不展示）

**第三步 · 排序沉底**

```sql
UPDATE v2_plan SET sort = 9999 WHERE id IN (2, 6, 7, 8, 9, 10, 11, 14, 18);
```
让它们在后台列表里全部沉到最底部，日常操作不会翻到。

### 3.3 顺手确认：现行档位是否齐全

清理后，在售商品应只剩：

| id | 名称 | 状态 |

| #17 | GPT Pro100 菲区 | show=1 |
| #19 | GPT Pro100 菲区2 | show=1 |

⚠️ **#19 与 #20 名称完全相同**（都是 `GPT Pro100 菲区2`，均 0 订单）——这看起来是**同一次配置操作留下的重复记录**。虽然你已确认"菲区"是代充行业特点不改名，但**这两个重复的记录建议确认一下是否都该在售**（详情见待确认清单第 2 条）。

> ⚠️ **Plus 权益价我从你给的 $16.50 调到了 $15.00**，理由在下面第 5.4 节，**这是本方案最需要你拍板的一处**。

### 5.3 权益包（按月，**不做年付**）

| 包 | 价格 | 权益次数 | 每次成本 | 定位 |
|---|---|---|---|---|
| **轻享包** | **$15 / 月** | 5 次 | $3.00 | 验证市场 |
| **畅享包** | **$99 / 月** | 50 次 | $1.98 | 稳定供货 |

### 5.4 ⚠️ 为什么建议把 Plus 权益价改成 $15

**现在的问题**：Plus 权益价 $16.50（省 $1.50），而一次权益的成本是 $1.98（畅享包）~ $3.00（轻享包）。

**也就是说：用权益买 Plus，用户是亏的。**

| 谁 | 花 | 省 | 结果 |
|---|---|---|---|
| 轻享包用户买 Plus | $3.00/次成本 | $1.50 | **亏 $1.50** |
| 畅享包用户买 Plus | $1.98/次成本 | $1.50 | **亏 $0.48** |

**为什么这很要命**：Plus 是流量款，是**用户最先接触的商品**。他在第一个商品上就发现"用权益反而更贵"，会直接判定这个包是套路，后面讲什么他都不信了。

**改法**：Plus 权益价 → **$15.00**（省 $3.00）
- 对轻享包用户：省 $3.00 = 成本 $3.00，**持平**（不赚不亏）
- 对畅享包用户：省 $3.00 - 成本 $1.98 = **赚 $1.02**

**代价**：Plus 的折扣率变深（$18→$15 = 16.7%，而 Pro 200 只降 6.5%）。**能不能承受取决于你的 Plus 成本** —— 如果 Plus 拿货成本在 $10 上下，$15 仍有 33% 毛利，可以承受；如果你告诉我实际成本，我可以帮你把这张表调到最优。

**若你不接受改价**，替代方案是：在商品卡上明确标注「**权益建议用在 Pro 系列更划算**」，把用户引导到高客单商品上。诚实但略啰嗦。
