## 0. 背景与定位

商城现有唯一购买入口是「**代充开通向导**」（FEAT-014：商品卡点击收口到向导，四步：登录 ChatGPT → 获取 Session → 选号 → 余额支付 → 自动开通）。

经典「**下单 → USDT 收银台 → 发卡（卡密）**」路径在后端全链路可用（v1.11.3 已做模拟支付端到端验证），但前台没有入口——它不是一个"坏掉的"流程，而是被设计性收起的第二条交付方式。

本方案要补的，不是新商品，而是**同一商品的第二种交付方式**：

| | 代充开通向导（现有） | 购买卡密（本方案） |
|---|---|---|
| 一句话 | **现场办** | **先买后用 / 可转赠** |
| 适合 | 自己、马上、有余额 | 送人、囤货、批量、USDT 直付、延后兑换 |
| 支付 | 仅余额（需先充值） | USDT 直付（收银台）或余额 |
| 本质差异 | 支付与开通同一时刻完成 | **支付与开通解耦**（卡密是交付凭证） |

设计原则：**同一商品、同一价格、两个入口**（主：立即办理／次：购买卡密）；不建议拆成两个独立 SKU（比价困惑 + 映射维护成本）。未来若要差异化定价，用"交付方式"配置留口子即可。

## 1. 适用场景（什么时候该用卡密路径）

| 场景 | 向导为什么不行 | 卡密路径怎么解 |
|---|---|---|
| **送朋友 / 家人** | 向导要求**当场登录目标 ChatGPT 账号**——送礼的人没有对方账号，结构上做不到 | 买下 → 把卡密发给对方 → 对方自行兑换 |
| **先囤后用 / 续费预购** | 向导"当下就办"，立刻改订阅状态 | 锁定当前价格，180 天内想兑再兑 |
| **批量 / 团队采购** | 一次只能办一个账号，N 个账号操作 N 遍 | 一次购买多张，逐张发放、逐张转赠（P3） |
| **不想先充值** | 向导仅余额支付 → 必须先充值，链路长且有"预付"信任门槛 | USDT 链上直付，付完拿卡 |
| **兑换条件当下不具备** | 卡在"取 Session"步骤即流失 | 先把购买完成，把高摩擦环节挪到用户方便时 |

反面：**自用 + 马上要 + 余额充足** → 向导仍是最短路径（少一次兑换环节）。卡密是**补位**，不是替代。

商家侧收益：购前摩擦最小化（转化率↑）、批量（客单价↑）、先收钱后交付（现金流前置，与"支付/履约分离"原则同构）。
风险边界：卡密是可转让凭证 → 防转卖灰产/套利/黑卡买单（限购、频控、支付风控）；**批量采购 ≠ 分销体系**，守住"不做分销提现/推广看板"红线。

## 2. P1（已实现 · v1.12.0）：入口 + 确认弹窗 + 复用存量链路

### 2.1 功能范围

1. **商品卡次级入口**：代充类目 & 在售态商品卡底部新增「购买卡密 · 送朋友 / 先买后用 →」（主按钮「立即办理」不动）。
2. **购买卡密确认弹窗**（主题注入内实现，风格对齐现有向导）：
   - 商品信息（名称 / 价格 / "经典购买 · 支付成功后系统自动发卡"）
   - 支付方式单选（来自 `GET /api/v1/user/order/getPaymentMethod`，默认选 USDT）
   - 当前余额展示（参考信息）
   - 说明区（后台可配文案：有效期 / 兑换方式 / 退换规则）
   - 「去支付」→ 自动执行 `order/save` → `order/checkout` → 新标签打开收银台
   - 完成态：订单号 +「打开收银台」兜底按钮 +「查看订单 →」（跳 `#/order/{trade_no}`）
   - 失败态：原因展示 +「重试」
3. **支付成功后走既有链路**：收银台（BEpusdt）→ 回调 → `order.open.after` → 自动发卡（CDK）→ 订单详情页展示「卡密 + 去开通」。

### 2.2 后台配置（Xboard 后台 → 插件 → KC 代充集成）

| 配置键 | 类型 | 缺省值 | 说明 |
|---|---|---|---|
| `card_buy_enabled` | boolean | `true` | **入口总开关**：关闭后入口立即消失（已进入的支付不受影响） |
| `card_buy_label` | string | `购买卡密` | 入口主文案 |
| `card_buy_hint` | string | `送朋友 / 先买后用` | 入口副文案（可留空） |
| `card_buy_notice` | text | 见 config.json | 弹窗说明文案；多条用换行或 `\|\|` 分隔 |

**生效机制（关键实现点）**：`/plan/kc-cards` 接口对 `card_buy_*` 采用**直读数据库**，绕过 Xboard 插件配置的 1 小时 `Cache::remember` —— 后台保存后**下一次请求即生效，无需重启/清缓存**，真正做到"随时关、随时开"。
（根因记录：Xboard 的 `HasPluginConfig::getPluginConfig()` 对插件配置有 3600s 缓存，且 `octane:reload` 不清 Laravel cache；P1 用直读规避，未改动任何 Xboard 内核。）

### 2.3 P1 验收（2026-10-10）

- 端到端（零真实扣款）：入口渲染 → 弹窗 → 下单（真实订单）→ USDT 收银台 → 模拟到账回调 → 自动发卡 → 订单详情页卡密可见；**幂等**（重复回调不重复发卡）。
- 开关：`card_buy_enabled=false` → 接口与页面入口**即时消失**；恢复 → 即时可见。
- 部署：本地注入源 === 线上 custom_html **逐字节一致**（md5 相同）。
- 证据：`debug_screenshots/cbbuy-*.png`、`debug_screenshots/cbbuy-notes.txt`；脚本 `archive/root-tmp-2026-10/_p1_card_buy_e2e.js`（v1.37.0 归档）。

## 3. P2 详细设计：卡密生命周期（我的卡密 / 提醒 / 分享 / 兑换联动）

> 目标：让"先买后用"的用户**看得见、找得到、被提醒**，把兑换摩擦降到最低。

### 3.1 「我的卡密」页（新）

- **入口**：用户中心新增「我的卡密」（导航「更多功能」下）；订单详情卡密卡内加「全部卡密 →」次入口。
- **列表字段**：卡密（等宽字体，默认打码显示中间段，点击复制）、套餐、来源订单号、购买时间、**有效期至**、状态、操作（复制 / 去兑换）。
- **状态口径**（与 KC 侧对齐）：
  | 前台状态 | 判定 |
  |---|---|
  | 待兑换 | 卡未使用且未过期 |
  | 已兑换 | KC 侧已使用（`kc_status=completed`） |
  | 已过期 | 超过 180 天有效期且未兑换 |
- **操作**：批量复制（多张时）、导出为文本（一行一张）、空态引导（"还没有卡密？去商品页看看 →"）。
- **数据来源**：插件新增 `GET /user/kc/cards`（登录态）：以 `v2_plugin_kc_cards` 按用户聚合（join `v2_order` 取归属），KC 状态沿用现有 kc_status 同步机制（回查接口），用 TTL 缓存（60s）防抖。

### 3.2 到期提醒

- **站内**（P2 必做）：列表页顶部提醒条「有 N 张卡密将在 7 天内到期」；订单页卡密卡加"临期"标签（≤7 天）。
- **触达**（P2 选做，需拍板）：邮件/Telegram 由 KC 侧既有"未兑卡提醒"承担（运营向）；用户向邮件提醒依赖邮件通道，列为开放问题。
- **阈值**：到期前 7 天开始提示（180 天有效期为基准，与后端一致）。

### 3.3 分享卡片

- 订单详情卡密卡加「分享给朋友」：复制一段模板文案（含套餐名、兑换指引、兑换链接 `http://<KC_HOST>/?cdk=XXX`）。
- 安全提示（分享面板上直接注明）：**链接即凭证**，谁持有都可兑换；请仅发给可信的人。
- 不生成图片卡片（避免额外依赖）；纯文本 + 链接即可满足送礼场景。

### 3.4 兑换页联动（KC 侧小改）

- 兑卡页已支持 `?cdk=` 直达；补两点：
  1. 从商城跳入时回显"来自商城订单 ××××"的上下文（沿用 URL 参数即可）；
  2. 把向导第 1–2 步的「Session 获取教程」复用到兑换环节（同一套图文，降低兑换流失）。
- 兑换成功后可选提示：「以后想直接自助办理，可用『立即办理』向导」。

### 3.5 接口与数据清单（P2）

| 接口 | 方法 | 说明 |
|---|---|---|
| `/user/kc/cards` | GET | 我的卡密列表（登录态；分页；含 state/valid_until/redeem_url） |
| `/user/kc/card` | GET | 已有（单订单查询），复用 |

### 3.6 P2 验收要点

- [ ] 「我的卡密」三类状态判定正确（含过期边界）
- [ ] 批量复制/导出内容与列表一致
- [ ] 临期提醒条出现/消失阈值正确（7 天）
- [ ] 分享文案中的兑换链接可直达且预填卡密
- [ ] 未登录 / 无卡密 空态正常

## 4. P3 详细设计：数量 1–10 与批量购买

> 约束：Xboard 原生 `order/save` **单笔单份**（一单一卡）。批量的本质是"一次操作触发多单"。

### 4.1 三条技术路线对比

| 方案 | 做法 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| A · 前端循环建单 | 数量 N → 循环 N 次 save → 逐个去支付 | 改动最小 | 支付 N 次，体验差 | 仅作兜底 |
| **B · 充值 + 余额秒付（推荐）** | 先按 N×单价充值余额（USDT 一次付清）→ 循环 N 笔**余额支付**订单（秒完成、自动发卡） | 用户只付一次；每单独立卡密；后端零改造（余额单已有"支付即履约"通路） | 依赖余额链路（已就绪） | **P3 主路径** |
| C · 合并支付单 | 自建"批量单"聚合 N 张卡一并支付 | 体验最佳 | 需新订单形态 + 对账/退款口径重构 | 远期，不排期 |

### 4.2 方案 B 交互设计（推荐）

1. 确认弹窗数量选 `1–10`（超 10 走客服/人工）；
2. 选「USDT 直付」时：提示"批量购买将先充值为余额，再自动逐张购买"（金额 = N×单价，一次性跳收银台）；
3. 支付成功后：自动执行 N 次余额下单（每次间隔 ~0.5s，展示逐张进度），全部完成 → 展示 N 张卡密清单（一键复制全部）；
4. 任一张失败：失败行标红 +「重试该张」，不影响已成功的；
5. 全部卡密进入「我的卡密」，可分别转赠。

### 4.3 风控与限额（P3 必做）

- 单账号**日购上限**（建议 ≤10 张/日，可配置）与频控（≥10s/单）；
- 大额/高频触发人工复核标记（与 KC 侧风控事件表对齐，不做自动封禁）；
- 明确写入规则：**批量购买不支持退款**（未兑换可走客服协商）。

### 4.4 配置扩展

在插件配置追加（沿用 P1 的"直读 DB"模式保证即时生效）：

| 键 | 默认 | 说明 |
|---|---|---|
| `card_buy_qty_max` | `1` | 单次购买上限（P3 上线后放开至 10；`1` = 旧行为） |
| `card_buy_batch_enabled` | `false` | 批量入口开关（与数量上限双重控制） |

### 4.5 P3 验收要点

- [ ] N=1 行为与 P1 完全一致（回归）
- [ ] N=10 全链路：一次充值 → 10 张卡逐张落库、逐张可兑
- [ ] 中途失败可单独重试且不重复发卡（幂等）
- [ ] 限额/频控生效；超限提示清晰

## 5. 风险与红线符合性

- **可转让凭证风险**：卡密可转赠 → 灰产转卖/套利可能是天然存在；对策 = 限购、频控、支付风控、有效期约束；本方案**不做**经销商/分销体系（与产品全景"明确不做"一致）。
- **兑换门槛不变**：兑换仍需提交目标账号 Session（安全约束：Session 不落库）；用教程与客服兜底，P2 的"教程联动"即为此。
- **载体**：本设计落在 **Xboard 过渡商城主站**；独立前台冻结期内不涉及，未来可直接复用。
- **不碰内核**：P1 全程未改 Xboard 内核（插件代码 + 主题注入 + 部署脚本），符合"保命补丁/插件 API/壳层"红线。

## 6. 开放问题（待拍板）
