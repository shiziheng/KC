# 双模式定价与对外分销 API 设计 v1.0.0

> **方案编号**：`SP-2026-10-13-API-v1.0.0`　**状态**：待评审（只出方案，不执行开发）
> **定位**：为《商品配置体验重构 v1.0.0》（`SP-2026-10-13-v1.0.0`）的**补篇**——两份方案一并评审，实施时并入同一分期计划
> **一句话**：同一货源、同一履约、**两个价格出口**——商城直客买固定零售价；下游客户通过 API 拿"上游成本 + 加价"的实时报价与商品

---

## 一、目标场景（用户原话拆解）

| # | 原话 | 设计解读 |
|---|---|---|
| 1 | 客户从我的平台直接下单，下单的是**固定商品价格** | 商城（Xboard）商品挂**固定零售价**（如 $15/月）：运营标价多少就卖多少，**不随上游成本波动** |
| 2 | 未来提供 API 出去 | 把 KC 作为**供货开放平台**，对下游分销商开放 API |
| 3 | API 根据**上游传来的价格加价**售卖 | 上游（Zovo）成本价是**动态的**；对外报价 = 成本 + **加价规则**（按比例/按固定额），成本一变报价跟着变 |
| 4 | 客户拿到我的 API 可以**直接拿到加价后的商品** | 下游调用 API 完成：查目录 → 报价 → 下单 → **拿到卡密/交付物**（同步返回或回调推送） |

**架构定性**：这不是两套系统，是**一套商品与货源数据 + 两个价格出口 + 一条共享履约链**：

```
货源成本（上游价·会波动）
   ├── 出口①固定零售价（运营手动设定·不变）→ 商城直客下单
   └── 出口②加价规则（成本×1.15 或 +$2）→ API 动态报价 → 下游客户下单
                     共享：库存/健康检查/履约（KC → Zovo → 自动发卡）
```

## 二、统一价格模型（核心设计）

### 2.1 四层价格概念

| 层 | 名称 | 谁定 | 何时变 | 出现位置 |
|---|---|---|---|---|
| L1 | **成本价**（上游价） | 上游同步/运营手填 | 随上游波动（定时同步） | 仅后台可见（货源区/利润核算） |
| L2 | **零售价**（固定） | 运营在商品定价里手设 | 只在运营改价时变 | 商城（客户看到并支付） |
| L3 | **加价规则** | 运营在商品上配置 | 跟成本联动 | 不直接露出，作用于 L4 |
| L4 | **报价**（API 价） | 系统按 `L1 + L3` 实时算 | 成本每次变动即变 | 对外 API（下游看到并支付） |

**要点**：L2 与 L4 **互不影响**——这是本设计的关键承诺。商城客户看到的 $15 永远是 $15；下游拿到的报价随上游成本浮动，赚的是稳定加成。

### 2.2 加价规则设计

```
报价 = f(成本, 规则, 保护)
  加价方式： ● 按比例  cost × (1 + p%)     例：成本 $10 × 1.15 = $11.50
            ○ 按固定额 cost + $x           例：成本 $10 + $2 = $12.00
  保护价（可选）： 报价低于保护价时按保护价出（防成本过低卖亏/卖乱）
  取整（可选）：   0.01 / 0.1 / 0.5 / 1 —— 报价美化（如 $11.53 → $11.60）
  客户级覆盖（后置）： 大客户可配专属加价率（默认继承商品规则）
```

- 精度：内部一律**分（cents）**计算，报价展示两位小数
- 无成本数据时：报价不可用（catalog 标记"暂不可售"），**不**用零售价顶替（防亏本卖）

### 2.3 成本同步机制

| 阶段 | 做法 |
|---|---|
| **MVP（本次规划）** | 运营在「上游管理 → 目录」为商品**手填成本**；提供"模拟调价"（±10%）用于验证报价联动与下游体验 |
| 接入真实上游后 | 定时任务（如每 30 分钟）拉取上游价 → 写 `upstream_price_cents` → 触发报价缓存失效；成本变动超阈值（如 >5%）时后台提醒 |
| 报表 | 每商品"成本/零售/报价"三线对照 + 毛利率看板（后续） |

## 三、商品配置体验升级（对《体验重构》向导的扩展）

### 3.1 「② 定价」步骤变成双区（一屏内）

```
② 定价
──────────────────────────────────────────────
 商城零售价（固定）      $ [ 15.00 ] /月
 ▸ API 分销定价          [ ● 开启 ]        ← 开关，不开则仅商城售卖
     加价方式   ● 按比例 [ 15 ] %    ○ 按固定额 $ [   ]
     保护价     $ [      ]（选填，防过低）
     取整       [ 0.1 ▼ ]
     ┌─ 报价模拟器（实时）──────────────────┐
     │ 当前成本 $10.00 → 对外报价 $11.50    │
     │ 成本 +10% $11.00 → 报价 $12.65       │
     │ 成本 -10% $9.00  → 报价 $10.35       │
     └──────────────────────────────────────┘
──────────────────────────────────────────────
```

### 3.2 其余触点

- **商品列表**：加一个小标记「API 已开 / 未开」；行内显示"成本 $10 → 报价 $11.50"
- **商品详情页**：新增「📡 API 分销」区块（规则同上 + 报价模拟器 + 该商品的下游调用量/成交额）
- **上游管理 → 目录**：成本列可编辑（MVP 手填入口）+「模拟调价」按钮
- 运营心智只需一句：**商城填"卖多少"，API 填"加多少"**

## 四、对外开放 API（v1）设计

### 4.1 接口面（新命名空间 `/api/open/v1/*`，与内部集成接口隔离）

> 现有 `/api/integration/*` 是 **Xboard → KC** 的内部集成（发卡）；对外 API 是 **下游客户 → KC** 的开放面，两者**鉴权、限流、审计独立**，互不复用密钥。

| # | 接口 | 作用 | 关键参数 → 响应 |
|---|---|---|---|
| 1 | `GET /api/open/v1/catalog` | 可售商品目录 | → `[{sku, name, price, currency, deliver:"card", available:true}]` |
| 2 | `POST /api/open/v1/quote` | 精确报价（可锁价） | `{sku, qty}` → `{quote_id, unit_price, total, currency, expires_at(60s), cost_basis}` |
| 3 | `POST /api/open/v1/orders` | 下单 | `{quote_id, client_order_no(幂等), qty}` → `{order_id, status, amount, cdk?}` |
| 4 | `GET /api/open/v1/orders/{order_id}` | 查单（含交付物） | → `{status: created/paid/delivered/failed, cdk, timeline}` |
| 5 | （我方 → 下游）`POST {callback_url}` | 异步交付回调 | 签名头 + `{order_id, status, cdk}`，失败重试 3 次（指数退避） |

### 4.2 鉴权与安全

```
请求头：
  X-Api-Key:    ak_live_xxxxx            （下游客户标识）
  X-Timestamp:  1712345678               （防重放：±5 分钟窗口）
  X-Signature:  HMAC-SHA256(secret, method + path + timestamp + body_hash)
安全项：
  · 双向：我们回调下游也签名（X-KC-Signature）
  · IP 白名单（客户可选开启）
  · 限流：默认 120 次/分钟（客户级可调），超限 429
  · 幂等：client_order_no 全局唯一（重复提交返回原单，不重复扣款/发货）
  · 审计：每次调用落 kc_api_quote_logs / 订单时间线
```

### 4.3 计费模式（MVP 推荐：预充值余额）

```
下游客户在「API 客户管理」预充值 → 余额账户
下单：校验余额 ≥ 订单金额 → 冻结 → 履约成功扣减 / 失败释放
余额不足 → 402 错误码（附当前余额）
（远期可选：月结/信用额度——本期不做）
```

### 4.4 报价锁价机制（分销 API 的关键工程点）

| 环节 | 规则 |
|---|---|
| 报价 | 生成 `quote_id`，锁价 **60 秒**（TTL 内下单价不变） |
| 下单校验 | ① quote 未过期 ② 下单量与报价一致 ③ **成本自报价后变动 ≤ 3%**（容忍度可配） |
| 冲突处理 | 超过容忍度 → `409 PRICE_CHANGED`（返回新报价，下游可重试）——**绝不在价格突变时静默按旧价成交或按新价扣款** |
| 下游选项 | 可显式传 `price_tolerance: "strict"（默认）/"accept_new"` |

### 4.5 错误码（统一信封）

```json
{ "success": false, "code": "PRICE_CHANGED", "message": "价格已更新，请重新报价",
  "data": { "new_quote_id": "q_xxx", "new_total": "12.65" } }
```
常用码：`INVALID_SIGNATURE / QUOTE_EXPIRED / PRICE_CHANGED / INSUFFICIENT_BALANCE / SKU_UNAVAILABLE / RATE_LIMITED / DUPLICATE_ORDER`

### 4.6 履约路径（复用现有引擎）

```
下游下单 → KC 自主履约（不经 Xboard）：
  kc_api_orders 建单 → zovocard-client（MOCK/真实）→ 拿到 CDK → 落库 → 同步返回 + 回调推送
库存/健康：下单前查 supplier-health（不可售 → SKU_UNAVAILABLE）
```

## 八、已做出的决策（无需再选）

1. **两个价格出口独立**：零售固定价与 API 加价价互不影响（商城价永不被成本波动打扰）
2. **加价方式**：按比例 / 按固定额二选一 + 保护价 + 取整（客户级覆盖后置）
3. **计费**：预充值余额先行（不做后付/月结）
4. **履约**：API 订单走 KC 自主链路（不经 Xboard），复用 zovocard-client 与健康检查
5. **报价**：60s 锁价 + 3% 成本变动容忍，超限强制重报价（409）
6. **接口面隔离**：`/api/open/v1/*` 与 `/api/integration/*` 分离，密钥/限流/审计独立
7. **成本来源**：MVP 手填+模拟调价；真实上游同步后置（预留同步器位）
