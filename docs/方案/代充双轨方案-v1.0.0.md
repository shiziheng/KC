# 代充双轨方案 v1.0.0

> 版本：v1.0.0（对应产品版本 v2.17.0）
> 状态：待实施
> 范围：把「平台直接代充」与「卡密代充」拆成两条互不干扰的业务路径

---

## 一、目标

同一条「代充」品类下，两个入口、两套资金与履约逻辑，互不串味：

| 路径 | 入口 | 顾客动作 | 平台动作 | 顾客拿到 |
| --- | --- | --- | --- | --- |
| **直接代充**（direct） | 商品详情「直接代充」 | 输入 ChatGPT Session、确认金额 | **冻结**该单金额 → 向上游发起开通 → 成功**扣款** / 失败**解冻** | 直接开通到账（无凭证） |
| **卡密代充**（cdk） | 商品详情「购买卡密」 | 选数量、下单 | **立即扣款**并发放 N 张 CDK | N 张卡密凭证（订单内可查） |

卡密代充拿到的凭证，顾客**之后随时**在「兑换卡密」页输入卡密 + Session 完成开通（兑换链路不变）。

## 二、边界（红线）

1. **不动 KC 原生 CDK 发放 / 兑换核心**：`cdk_codes`、`integration_cdk_issue`、`store.issueCdkByRef`、`POST /api/verify-cdk`、`POST /api/run-process` 的语义与实现一律不改。本次改动只落在**自有订单层**（`kc_api_orders` / `kc_customers` / `kc_customer_wallet_ledger`）。
2. **对外分销 API（`/api/open/v1/*`）行为不变**：仍为「下单即从租户余额扣款 + 同步发 1 张卡」，`createApiOrderCore` 的 open_api 路径零改动。
3. **非代充商品（成品号 / 建站服务）行为不变**：仍为下单即扣款并交付卡密（`fulfill_mode='auto'`）。
4. 资金两条账本严格分离（顾客钱包 vs 租户余额）——沿用 R2 红线。

## 三、数据层变更

| 表 | 变更 | 说明 |
| --- | --- | --- |
| `kc_customers` | `+ held_cents INT NOT NULL DEFAULT 0` | 冻结金额（分）；`balance_cents` 语义收敛为「**可用**余额」 |
| `kc_customer_wallet_ledger` | `type` ENUM 扩 `hold` / `capture` / `release` | 冻结 / 核销 / 解冻三类留痕 |
| `kc_api_orders` | `+ fulfill_mode ENUM('auto','direct','cdk') NOT NULL DEFAULT 'auto'` | `auto`=历史/对外API/非代充；`direct`=直接代充；`cdk`=卡密代充 |
| `kc_api_orders` | `+ hold_cents INT NOT NULL DEFAULT 0` | 该单当前冻结额（0=无冻结），作幂等闸门 |
| `kc_api_orders` | `+ cdk_list_json TEXT NULL` | 卡密代充的 N 张卡密数组；`cdk` 列保留=首卡（兼容原生开通驱动与历史对账） |

**为什么历史单默认 `auto` 而非 `direct`**：历史代充单是「先扣后退」模型（下单即扣款、失败才退回），若标成 `direct` 会让对账误判为「有冻结」而重复加钱。`auto` 保持历史语义。

## 四、资金流时序

### 4.1 直接代充（冻结 → 核销 / 解冻）

```
下单：
  balance_cents -= amount        （可用 ↓）
  held_cents    += amount        （冻结 ↑）
  流水 type='hold'  change=-amount
  kc_api_orders: status='created', fulfill_mode='direct', hold_cents=amount
  → 内部发 1 张「不展示给顾客」的卡密（仅作原生开通任务引用），返回该 cdk
  → 前端逐账号提交 /api/run-process（KC 原生链路，一字未改）

上游成功（任务终态 success）：
  held_cents -= amount           （冻结 ↓，可用不变）
  流水 type='capture' change=0   （余额在冻结时已离开「可用」，此处只核销冻结）
  kc_api_orders: status='delivered', hold_cents=0

上游失败（任务终态 failed）：
  held_cents    -= amount
  balance_cents += amount        （解冻回可用）
  流水 type='release' change=+amount
  kc_api_orders: status='failed', hold_cents=0, fail_reason=…
```

幂等闸门：`capture` / `release` 都以「订单状态原子改判 + `hold_cents>0`」作为准入条件（`affectedRows=0` 即跳过），配合钱包流水 ref 判重，绝不重复加减。

### 4.2 卡密代充（立即扣款 + 发 N 卡）

```
下单：
  balance_cents -= amount
  流水 type='consume' change=-amount
  issueCdkByRef(ourOrderNo#1..#N)  → N 张 CDK
  kc_api_orders: status='delivered', fulfill_mode='cdk', cdk=首卡, cdk_list_json=[…N 张…]
  → 前台把 N 张卡密凭证一次回吐给顾客
```

兑换：顾客之后在「兑换卡密」页输入卡密 + Session，走原生 `verify-cdk` + `run-process`（本方案不改）。

## 五、订单状态机

| fulfill_mode | `created` | `delivered` | `failed` |
| --- | --- | --- | --- |
| `direct` | 冻结中（开通进行中 / 未启动） | 已完成 · 已扣款 | 失败 · 已解冻 |
| `cdk` | —（下单直落 delivered） | 订单完成 · 持卡密凭证 | 履约失败（下单即失败，余额已退回） |
| `auto` | 历史/对外 API 在途（不变） | 已完成（不变） | 失败（不变） |

## 六、对账改造（`reconcileFailedActivationsOnce`）

三桶处理，互不干扰：

1. **直接代充在途**（`fulfill_mode='direct' AND status='created' AND hold_cents>0`）：
   - 任务终态 `success` → `capture`（补上 worker 钩子漏掉的场景，如进程重启）；
   - 任务终态 `failed` → `release`；
   - 无任务且账龄超阈值（`ACTIVATION_HOLD_UNSTARTED_TIMEOUT_MS`，默认 30 分钟）→ `release`（未启动开通，解冻）；
   - `manual` / `maintenance` / 进行中 → **保持冻结**待人工。
2. **已核销却事后失败**（`fulfill_mode IN ('auto','direct') AND status='delivered' AND cdk<>''`）：沿用既有 `refundOrderOnActivationFailure`（退回余额）。
3. **卡密代充（`fulfill_mode='cdk'`）不参与退款对账**：卡密是顾客买到的凭证，兑换失败时卡密会回滚为未使用、顾客可重试，不自动退款。

## 七、与 KC 原生链路的关系

- 直接代充：**内部仍发一张不展示给顾客的卡密**驱动 `/api/run-process`（原生要求必须有 cdk 且 `type='自助'`）。本方案不改原生，只在自己的订单层加「冻结/解冻」钩子挂在两个 worker 的终态落点。
- 卡密代充：直接复用 `issueCdkByRef` 发 N 张真实卡密；顾客兑换走原生校验 + 开通。
- 因此「原生 CDK 发放/兑换」这条轴完全不动；新增的只是「我们如何记账 + 什么时候把冻结转成扣款」。

## 八、前台设计

### 8.1 详情页（代充品类）二选一

- 两个并列入口卡片：
  - **直接代充**：说明「输入 Session，平台代你开通到账」→ 进入现有 5 步呈递向导（① 登录 → ② 取 Session → ③ 提交 → ④ 确认账单 → ⑤ 进度），**账单页文案改为「冻结」口径**。
  - **购买卡密**：说明「先买卡密，之后随时兑换」→ 打开卡密购买弹层（选数量 N → 显示总价与余额 → 下单）→ 下单成功展示 N 张卡密凭证（一键复制 + 「去兑换」）。
- 非代充商品（成品号 / 建站服务）保持原「立即购买」单入口。

### 8.2 订单中心

按 `fulfill_mode` 分支：
- `direct`：时间线口径改为「已下单（冻结金额）→ 已提交开通 → 开通完成（已扣款）/ 开通失败（已解冻）」；
- `cdk`：详情弹层展示**卡密凭证列表**（N 张，各带复制）+「去兑换」入口，时间线为「已下单 → 已支付 → 卡密已发放 → 待兑换」；
- `auto`：不变。

## 九、需用户确认的边界

1. **多卡 DDL 变更**：`cdk_list_json` 采用 TEXT 承载 JSON 数组（不新增关联表），`cdk` 保留首卡以兼容既有对账与原生引用。
2. **退款对账改造**：由「一律退回」改为「有冻结则解冻、无冻结（历史单）则退回」，并新增「未启动开通超时解冻」判定。
3. **未启动超时阈值**：默认 30 分钟（`ACTIVATION_HOLD_UNSTARTED_TIMEOUT_MS` 可调）。

## 十、验收口径

- 功能：F1 冻结→上游成功→已扣款（冻结归零、可用不变）；F2 冻结→上游失败→已解冻（可用回补、冻结归零）；F3 卡密代充一单发 N 张卡密且可兑换；F4 幂等（重复结算不重复加减）。
- UX：U1 详情页两入口在同一屏可辨、不误导；U2 卡密凭证可复制；U3 窄屏无横向溢出、0 业务 console error、金额全 `$`。

## 十一、回滚

本方案仅新增列与新增逻辑，无破坏性变更：
- 代码回滚：还原 `server.js` / `mysql-store.js` / `public/site/index.html` 即可（`fulfill_mode` 默认 `auto`，既有单不受影响）；
- 数据回滚：新增列可保留（默认值即历史语义），`held_cents` 需将未结算的直接单先 `release` 再回滚。
