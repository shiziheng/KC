# 后台用户与账号管理方案 v2.2.0

> 版本：v2.2.0（**扩充重写**，取代 v1.0.0 / v2.0.0 / v2.1.0）　日期：2026-10-16　状态：**待评审（未实施）**
> 关联：VERSION.json（拟 v2.3.0 起）、docs/产品全景.md、server.js、mysql-store.js、public/admin.html、public/tenant-admin.html

## 〇、判断（先给结论）

本方案经三轮补全，最终认定：后台缺的**不是几个页面，而是「账号治理」这一整套平台底座**。缺口分四层：
① **看不到也给不了**前台顾客（列表/详情/余额/权益/订单/账单/冻结/改密）；
② **管不了后台自己**（平台只有**一个硬编码管理员**，无多账号/角色）；
③ **没有基础平台能力**（**角色权限、菜单管理、密码重置**、会话与登录安全）；
④ **没有记账**（零操作审计）。

本版（v2.1.0）在 v2.0.0 基础上**补全 ③**，并新增 **§一 战略决策：自研 vs 迁移 Xboard**。

## 一、战略决策：完全自研，不迁移 Xboard 原生

这是你问的核心问题。**结论：完全自研（KC 原生），仅借鉴 Xboard 的 RBAC 范式，迁移代码不可行也不必。**

| 维度 | **完全自研（KC 原生）** | 迁移 Xboard 原生 |
|---|---|---|
| 技术栈 | Node/Express（沿用现有单进程） | PHP/Laravel（异构，无一行业务可复用） |
| 项目既定方向 | ✅ 一致 | ❌ **直接冲突**：历史指令 =「彻底摘除 Xboard、不再引用任何 Xboard 代码」 |
| 账号体系 | 复用 `kc_customers` / `kc_tenant_staff` / 管理员 | `v2_user`/`v2_admin`/权限组为**旧谱系、已退场** → 迁移 = 双账号体系并存 |
| 多租户 | KC 已按 Host 识别租户 | Xboard 无多租户，节点/订阅模型与 KC 不匹配 |
| 运维 | bind mount 热改，单容器 | 需复活**已停容器**+ 重放注入链（动用回滚安全网） |
| 审计与可测性 | 全在本次方案内可控可测 | 跨语言、跨进程，测试与排障成本高 |

**采纳的结论**：
- **自研实现**（用 KC 的 Node/Express + MySQL + admin.html）。
- **借鉴范式**：Xboard「**权限组 / 角色 → 权限点 → 菜单**」的三段式权限模型思路，用 KC 技术栈重写（模型可借鉴，代码不迁移）。
- **不借鉴**：Xboard 的 PHP 实现、节点/流量/订阅/权限组**数据模型**、其账号表——这些要么技术栈不通，要么已随 Stage 3 退场。

**三条硬理由**：① 与「摘除 Xboard」既定方向冲突；② 技术栈异构，迁移 ≈ 重写，只是把工作量搬到 PHP；③ KC 已有自己的账号与多租户体系，Xboard 账号体系已退场，迁移必然造成双体系并存与租户作用域混乱。

## 三、优化建议（方案 + 理由 + 优先级）

### 3.1 [P0] 前台顾客管理域（技术后台 + 代理商后台）
- **只读**：列表（分页/搜索/筛选）、详情（余额+聚合）、权益、订单、账单（钱包流水+充值单）；代理商侧镜像、作用域收窄 `req.tenant.id`、**剔除成本**。
- **写（v2.0.0 漏掉）**：冻结/解冻、重置密码、备注/昵称、手动开号。
**理由**：账号承载**资金与资产**，连"冻结异常账号"都做不到 = 资金安全裸奔。
> 冻结/解冻在上上版被删，我**建议恢复**（资金安全底线）；你若不认可降 P2，但属有意取舍。

### 3.2 [P0] 平台管理员账号域
- 新表 `kc_admin_users` + `/api/admin/admins`（列表/创建/编辑/禁用/重置密码/改角色）；把现有单账号**迁移**为首个 `super`，旧登录兜底。
**理由**：**「后台不能管后台」比「后台不能管顾客」更刺眼**，且是权限与审计的地基。

### 3.3 [P0] 角色与权限域（RBAC 三段式，自研）
- **角色**：`kc_admin_roles`（`code/name/permissions_json/builtin`）；内置 `super / operator / viewer / finance`，支持自定义。
- **权限点（建议清单）**：`admin.read|write`、`role.read|write`、`menu.read|write`、`customer.read|write`、`order.read`、`pricing.read|write`、`entitlement.read|issue`、`tenant.read|write`、`audit.read`、`system.config`。
- **校验**：复用 `authenticateAdmin` 叠加 `requirePermission('point')`；租户侧沿用 `requireTenantOwner`。
- **分配 UI**：管理员编辑弹层里的「角色 → 权限点」勾选矩阵。
**理由**：没有 RBAC，3.2 的多管理员就是「多人共用一把全权钥匙」；最小权限与追责无从谈起。

### 3.4 [P1] 菜单管理域（自研，动态菜单）
- 新表 `kc_admin_menus`（`key/label/icon/group/sort/permission/visible`）+ `/api/admin/menus` CRUD。
- 前端菜单**由硬编码 DOM 改为数据驱动**：登录后拉取菜单、按当前角色权限**过滤**渲染，保留现有页面容器（只换"从哪来"）。
- **边界**：只做「菜单项/显隐/排序/图标/权限绑定」，**不做**页面内容自定义（不造低代码平台）。
**理由**：硬编码菜单导致「加个页面要改 HTML」，且无法按角色收口（否则 `viewer` 也能看到删除入口）。

### 3.5 [P0/P1] 密码与账号安全域（四场景 + 自助 + 登录安全）
- 新表 `kc_password_resets`（`token/account_type/account_id/expires_at/used_at/created_by`）。
- **四种重置场景**：① 平台 **super 重置其他管理员**（＋自助改密，已有）；② **租户 owner 重置 staff**（＋owner 自助改密）；③ **管理员重置顾客**（生成一次性临时密码/重置链接 + **强制首次改密**）；④ **顾客自助「忘记密码」**（邮箱/TG 验证）。
- **登录安全策略**：失败锁定阈值（现有）、**会话超时与强制下线**、**密码强度**、**强制首次改密**、2FA 由平台**下放租户 owner**。
**理由**：密码重置是所有账号体系的基本盘；现状管理员只能"改自己的"，用户遗忘即永久锁死——这是运营级阻断。

### 3.6 [P1] 租户员工管理完善
- 在已有 GET/POST 上补 `PUT /staff/:id`（改角色）、`POST /staff/:id/status`、`POST /staff/:id/reset-password`；表已具备 `status/password_hash`，**不改表**。
**理由**：代理商只有「加人」没有「管人」。

### 3.7 [P1] 操作审计
- 新表 `kc_audit_logs`（`actor_type/actor_id/actor_email/action/target_type/target_id/before_json/after_json/ip/created_at`）+ 写操作中间件自动落库。
**理由**：改价/发权益/删卡/改顾客/改账号都是**高危写操作**，无审计=出事无法定位到人；也是 3.3 角色的配套。

## 四、统一权限模型（RBAC 三段式）设计要点

```
主体(platform_admin/tenant_owner/tenant_staff/customer)
   └─ 角色(kc_admin_roles: super|operator|viewer|finance|自定义)
        └─ 权限点(permission points)
             └─ 菜单可见性(kc_admin_menus.permission) + 端点校验(requirePermission)
```
- **主体**：`platform_admin` / `tenant_owner` / `tenant_staff` / `customer`。
- **复用**：`authenticateAdmin`（server.js L662）/ `authenticateTenantStaff`（L1798），叠加 `requirePermission('point')`。
- **铁律**：租户作用域一律取 `req.tenant.id`，禁止从请求体读 `client_id`；成本/上游通道不对租户暴露。

## 六、实施批次与版本（推荐顺序）

1. **v2.3.0**：[P0] **顾客管理域**（技术后台 + 代理商后台：只读 + 冻结/改密/备注/开号）。
2. **v2.4.0**：[P0] **平台管理员账号域 + 角色权限（RBAC 三段式地基）**。
3. **v2.5.0**：[P0/P1] **密码与账号安全（四场景重置 + 自助 + 登录安全）** + 操作审计。
4. **v2.6.0**：[P1] **菜单管理**（菜单配置化 + 按权限过滤渲染）。
5. **v2.7.0**：[P1] **租户员工完善**（改角色/禁用/重置密码）。
6. **v2.8.0**：[P2] 权限点细化 / 按权限显隐收口。

**顺序理由**：先补「两头看不见」（顾客 / 后台账号），再立「地基」（角色权限 + 密码安全 + 审计），最后做「体验与收口」（菜单管理 / 租户员工 / 细粒度权限）。

## 七、验收标准（每批次：功能测试工程师 ≥3 + UX 专家 ≥3）

**共性关键断言**
- 顾客域：`balance` 与 `balance_cents` 一致；订单按 `customer_id` 计数一致；权益按 `customer_id` 命中（不与 `user_id` 串账）；代理商侧仅见本租户、**无 `cost_cents`**、越权返空/403。
- 管理员域：**迁移后原单账号仍能登录**；禁用后登录被拒；非 `super` 不能增删管理员。
- RBAC：低权限角色访问越权端点返回 403；`requirePermission` 覆盖新端点。
- 菜单域：菜单由数据驱动；按角色过滤后 `viewer` 看不到写操作入口。
- 密码域：四场景各能重置；一次性令牌**用过即失效/过期**；重置后强制改密生效。
- 审计域：任一高危写操作后 `kc_audit_logs` 有 `actor/action/target/before/after` 记录。
- UX：分页/搜索 loading 与空态、详情抽屉多 tab 不破版、金额一律 `$`、术语无「会员/等级/VIP」。

## 八、风险与非目标

**风险**：① 单账号→多账号迁移需兼容旧登录与会话；② RBAC/菜单数据驱动改造会波及整个 admin.html 渲染路径，需回归 23 个 tab；③ 密码重置需接邮件/TG 通道（依赖现有 `getTelegramConfig`）；④ 顾客 `disabled` 即时生效需改 `authenticateCustomer` 前置校验。
**非目标**：不做顾客侧（前台）改造；不做提现/退款工单；不做第三方 SSO/扫码登录；**不迁移 Xboard 任何代码**（仅借鉴其 RBAC 范式）；不重复造节点/流量/订阅能力。

## 九、与现有 KC 后台功能的重合与去重

**现有技术后台菜单**（admin.html L1777-1879，18 项 + 2 折叠组）：概览中心 / 系统配置 / 代理池 / 浏览器池 / 免税地址 /〔支付与资产：支付链接调试·银行卡池·CDK 管理·Session 管理·账单记录〕/ 续费管理 /〔任务与日志：任务管理·自动化任务·运行日志·登录日志〕/ 站点与定价 / 商品管理 / 权益 / 权益报价 / 上游管理 / API 客户 / 租户。

| 本方案新增域 | 与现有是否重合 | 处置 |
|---|---|---|
| 顾客管理 | 无重合（后台**无任何顾客维度页面**） | **新增** |
| 平台管理员账号 | 无重合（仅单账号 + 登录日志） | **新增**；「登录日志」保留原页，作为其下钻 |
| 角色与权限 | 无重合 | **新增** |
| 菜单管理 | 与"硬编码菜单"**重合（同一物）** | **改造**：用数据源替换硬编码，不是再建一套 |
| 密码重置 | 部分相邻（「改密」「2FA」已存） | **新增**，与现有「改密/2FA」合并为「账号安全」 |
| 操作审计 | ⚠️ 易与「运行日志/登录日志」混淆 | **新增**，明确区分：现有的=**系统/任务日志**，新的=**操作审计**（谁改了什么） |
| 租户员工完善 | 与现有「租户」页 + 代理商后台 staff **重合** | **不新增顶级菜单**，并入「租户」详情内「员工」tab |
| 顾客权益查看 | 与现有「权益」页 `user-lookup` **重合** | **去重**：权益页保留"规则与发放"，顾客维度权益归「顾客详情」，`user-lookup` 降级为跳转入口 |

**三条关键去重决策**（避免"看着能管、其实是另一套"）：
1. 「**账单记录**」= 平台侧**开通账单**（ChatGPT 扣款），**不是**顾客钱包账单 → **建议改名「开通账单」**；顾客账单只出现在「顾客详情 → 账单」。
2. 顾客订单/账单**不做**顶级菜单，只在「顾客详情」内聚合（避免与「支付与资产」组生出第三套订单视图）。
3. 「权益」页 ↔「顾客」页边界：**规则 / 发放 / 报价**在权益侧，**单个顾客持有什么**在顾客侧。

## 十一、关键业务操作流程

### F1 顾客冻结 / 解冻
入口：顾客列表 → 行 → 冻结/解冻 → 二次确认（显示当前余额与未完成订单数）
1. 校验权限：技术后台 `customer.write`；代理商后台 owner/staff
2. 作用域：技术后台按选中顾客；代理商后台强制 `client_id = req.tenant.id`
3. 更新 `kc_customers.status`
4. `authenticateCustomer` 前置校验 `status`（**前提：改造登录 / 下单中间件**，否则冻结不即时生效）
5. 落审计：`action=customer.freeze|unfreeze, target=customer:<id>, before/after=status`
6. 效果：冻结后不能登录 / 下单；**已有余额与订单保留**（不没收），退款走人工
反馈：Toast + 列表状态徽标变色。

### F2 密码重置（四场景统一抽象）
统一机制：生成一次性 `kc_password_resets` 令牌（32B 随机、存 hash、30 分钟过期、**一次有效**）。
- **A. 平台 super 重置管理员**：后台账号 → 重置 → 生成临时密码（**强制首次改密**）→ 审计
- **B. 租户 owner 重置 staff**：代理商后台 → 员工 → 重置 → 同 A
- **C. 管理员重置顾客**：顾客详情 → 重置密码 → 临时密码 / 重置链接 → 强制首改
- **D. 顾客自助找回**：前台「忘记密码」→ 邮箱/TG 验证 → 重置链接 → 设新密码（**属顾客侧，另一批**）
统一规则：令牌**用后即焚**；重置必须审计（actor/target）；**不明文回显**密码（临时密码仅展示一次）。

### F3 角色与权限分配
1. 角色页：新建/编辑角色 → 勾选「权限点矩阵」→ 保存 `kc_admin_roles.permissions_json`
2. 后台账号页：编辑账号 → 选角色（单一角色，先不做多角色）
3. 生效：`requirePermission(point)` 中间件 + 菜单按 `kc_admin_menus.permission` 过滤
4. 落审计：`role.write / admin.write`
5. 内置角色 `builtin=true` **不可删**，仅可查看

### F4 菜单配置（数据驱动）
1. 菜单管理页：增删菜单项（`key/label/icon/group/sort/permission/visible`）
2. 保存 → 更新 `kc_admin_menus`
3. 前端登录后拉取菜单渲染；`visible=false` 或权限不足则不渲染
4. 边界：**不含**页面内容自定义（不造低代码）

## 十二、后台使用场景分析

**角色（actor）**：① 平台超管 `super`；② 平台运营 `operator`；③ 平台客服 `viewer/cs`；④ 租户 owner；⑤ 租户员工 staff；⑥ 前台顾客（数据来源，不登后台）。

| 场景 | 主角色 | 频次 | 关键需求 | 落到谁家 |
|---|---|---|---|---|
| S1 每日巡检（新增顾客 / 当日订单 / 充值到账） | 运营 / 超管 | 每日 | 概览 + 顾客列表 + 订单筛选 | 技术后台 |
| S2 顾客问询（按邮箱找人 → 余额/权益/订单/账单） | 客服 | 高频 | 顾客详情一站式 | 技术后台 / 代理商后台 |
| S3 异常处置（投诉未到账 → 对流水/订单 → 冻结/退款/补发） | 客服 | 中频 | 流水 ref ↔ 订单，冻结能力 | 两端 |
| S4 财务对账（某日充值/消费/退款、余额增减） | 运营 | 每日 | 账单汇总 + 导出（本期不做导出） | 技术后台 |
| S5 账号治理（招人开号 / 分配角色 / 离职禁用） | 超管 | 低频 | 管理员 CRUD + RBAC | 技术后台 |
| S6 高危变更留痕（改价/发权益/删卡 → 事后追责） | 超管 | 按需 | 操作审计 | 技术后台 |
| S7 密码救急（员工/顾客遗忘） | 超管 / owner / 客服 | 中频 | 四场景重置 | 两端 |
| S8 代理商自助（owner 管本租户顾客与员工） | 租户 owner | 中频 | 租户作用域视图 | 代理商后台 |

**三个主场景（最有代表性，验收以此为准）**
- **S2 顾客问询**：输入邮箱 → 顾客列表命中 → 详情「概览」看余额 + 「权益」看剩余次数 + 「订单」看买了什么 + 「账单」看余额流水，一次看全，不用跨三个页面拼。
- **S3 异常处置**：流水里找到 `ref=充值单/订单号` → 跳订单看状态 → 若账号异常则**冻结** → 必要时**重置密码** → 全程落审计。
- **S5 账号治理**：超管新建运营账号 → 勾权限点 → 离职时**禁用**而非删号（保审计连续）。

## 十三、账单与订单信息设计（本轮重点）

### 13.1 顾客账务三视图（顾客详情 → 「账单」tab）

| 视图 | 数据源 | 说明 |
|---|---|---|
| **A. 余额流水（钱包账单）** | `kc_customer_wallet_ledger` | **顾客余额变动流水**（你定义的口径） |
| **B. 订单** | `kc_api_orders` | 按**类型**分组/筛选（见 13.3） |
| **C. 充值单** | `kc_customer_recharges` | 充值入账的原始单据（链上收款） |

三视图以 `ref / 单号` **互相关联**：流水 `ref` = 订单号或充值单号；充值单回调写流水 `type=recharge`；下单写流水 `type=consume, ref=order_no`。

### 13.2 余额流水设计

列：`时间 | 类型 | 变动(±$) | 变动后余额 | 关联单号 | 备注`

- **类型规范**（扩展 `type` 枚举）：`recharge` 充值入账 · `consume` 下单消费 · `refund` 退款 · `adjust` 人工调账。
- **消费细分**：在 `ref`/`note` 体现消费归属（`consume:topup|account|website|pack`），与 13.3 的订单类型对齐。
- **口径铁律**：`balance_after_cents` 必须**链式自洽**（逐条累加 = 当前 `kc_customers.balance_cents`）；金额分→美元、统一 `$`。
- **汇总**：`summary{ recharge_total, consume_total, refund_total, balance }`（均 `$`）。

### 13.3 订单类型设计（核心补充）

**现状**：`kc_api_orders` **无类型列**，只有 `sku_code`（INSERT 见 server.js L7442）；但**商品目录已带 `category`**（`/api/tenant/catalog` 返回 `category`，server.js L2022/L2036），并有 `categoryKeyNorm`（L5842）归一化。

**方案：新增列 `kc_api_orders.biz_type`**（下单时**定格**，避免目录事后改类导致历史失真）：
- 枚举：`topup` 代充 · `account` 成品号 · `website` 建站服务 · `entitlement` 权益包 · `other` 其他
- 来源：下单时取该 SKU 的 catalog `category` 映射（`recharge→topup`、`account→account`、`website→website`、`pack→entitlement`，其余 `other`）
- 历史回填：按 `sku_code` join 目录 `category` 做一次性 UPDATE
- **单一事实源建议**：把 `categoryKeyNorm`（L5842）统一成**前端 / 商品目录 / 订单**共用的一套 key，消除两套映射漂移

**订单列（顾客详情 → 订单）**：`时间 | 类型 | 订单号 | 客户单号 | 商品(sku) | 数量 | 金额$ | 状态 | 卡密 | 来源`
- 状态口径沿用现有：`created→处理中 / delivered→已完成 / failed→失败`
- 筛选：按 **类型 / 状态 / 时间 / 来源**（`open_api|tenant_web`）
- 成本 `cost_cents` **仅技术后台可见**，代理商侧剔除

**类型 ↔ 前台导航 ↔ 数据源（统一映射表）**

| 前台导航 | 品类 key | `biz_type` | 数据源 |
|---|---|---|---|
| 代充 | `recharge` | `topup` | `kc_api_orders` |
| 成品号 | `account` | `account` | `kc_api_orders` |
| 建站服务 | `website` | `website` | `kc_api_orders` |
| 权益包 | `pack` | `entitlement` | `kc_api_orders`（+ `kc_entitlement_grants`，`source=purchase`）|
| 其他 | `other` | `other` | `kc_api_orders` |

> ⚠ **待核实**：权益包开通是否落 `kc_api_orders`（走同一 `createApiOrderCore`）还是仅写 `kc_entitlement_grants`。本设计**假定与普通下单同源**（sku=`pack_*`）；若不成立，则订单视图另取权益来源合并。实现前须先核实（可 Grep `buyPack` 落库路径）。权益订单金额应呈现**双价**（原价 / 权益价 / 抵扣），字段已在 `kc_entitlement_uses`（`original_cents / final_cents / discount_cents`）。

### 13.4 API 设计补充

- `GET /api/admin/customers/:id/wallet` → `ledger[] + recharges[] + summary{}`
- `GET /api/admin/customers/:id/orders?biz_type=&status=&page=` → **支持 `biz_type` 筛选**
- （可选，便于 S1/S4）`GET /api/admin/orders?biz_type=&status=&from=&to=&page=` 全局订单；**默认不做顶级菜单**（避免与「支付与资产」组重复），可先作为概览中心的一个入口卡。
