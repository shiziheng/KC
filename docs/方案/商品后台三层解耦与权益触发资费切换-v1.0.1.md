# 商品后台三层解耦与权益触发资费切换

> 方案编号：`SP-2026-10-11-v1.0.1`　文档状态：**待用户审核**
>
> 来源：2026-10-11 下午用户提出 ——「后台商品配置包括接通上游、商品卡片配置、资费配置，三个部分分开设置；更换上游 / 调整资费都要方便；后续场景：客户买权益类商品后自动将相关商品设置为另一个资费包」。
> 基线：`v1.14.0`；关联方案：`SP-2026-10-11-v1.0.0`《商品类型体系与交付设计》、`SP-2026-10-09-v1.0.0`《系统低耦合重整与上线路线》、`SP-2026-10-10-v1.0.0`《后台形态选型》、`IF-2026-10-11-v1.0.0`《运营台契约 v1》。
> 本方案只定模型、边界与分期；不含代码。审核通过后按 §9 分期执行（每段停下确认）。

---

## 0. 一页结论

1. **三层解耦**：把现在绑在 v2_plan 一行上的三件事拆成三个独立配置面 —— ① **上游接入层**（谁在卖、卖什么）、② **资费层**（我们卖多少钱）、③ **商品展示层**（前台看到的样子）。换上游只改①，调价只改②，文案换皮只改③。
2. **三个独立后台页**：上游接入 / 资费配置 / 商品卡片，**三个 Tab / 三个独立路由**，互不依赖（与现有「商品卡片配置」合并、扩成完整三栏）。
3. **权益触发资费切换 = 价格层切换**：客户买权益 → 系统给用户发"权益资格"（grant）→ 用户再下相关商品时，**价格引擎按 grant 自动取最优权益价**（无须用户操作、不改 plan 实体）。MVP 先做"价格切换"；后续可扩展"动作切换"（自动执行某动作）。
4. **不破红线**：所有改动走 KC 新表 + 插件 API + 运营壳页面（与《后台形态选型》《运营台契约 v1》一脉相承）；Xboard 内核不动；`v2_plan` 仍作"展示 SKU"行但**不再承载资费/上游键**，由新表一对多引用。
5. **数据双轨**：迁移期保留旧字段读路径，新接口先行；UI 提示"新版生效"过渡；旧字段在验证稳定后下掉。
6. **待拍板 6 项**（§10）；其中 1 项与红线相关 ——"权益资格能给储值型商品下单价打折" 需用户确认是否扩大权益边界。

## 1. 现状问题（耦合点定位）

**基线**：v1.14.0 的数据模型，运营视角下"一个商品"≈ 一行 `xboard.v2_plan`，但这行同时承载：

| 耦合点 | 现在放在哪 | 后果 |
|---|---|---|
| **上游套餐键映射** | `plugins.config.packages`（`{plan_id → "plus"|"pro_5x"|...}`） | 换上游要改插件 config；与 KC 表无引用关系，回滚困难 |
| **上游健康度** | KC 侧 `supplier-health.js` + 插件 `SupplierHealthClient` | 健康度穿透到卡片展示层（onsale/soldout），改健康度逻辑会动展示逻辑 |
| **充值包金额 / 是否充值包** | `v2_plan.kc_is_topup`、`kc_topup_amount` | 与 SKU 字段混在同一行；充值价改不动 SKU 历史价 |
| **周期价（按月/季/年...）** | `v2_plan.month_price/quarter_price/.../prices(JSON)` | 调价要逐行改；促销期间"全周期临时打折"做不到（无 SKU 概念） |
| **卡片展示配置** | `v2_plan.kc_card`（标题、副标题、价、优惠行、类型标、chips、guarantees...） | 展示层改版要连带改 SKU 行；权限粒度粗 |
| **权益价** | **未实现**（权益方案 §5 设计中，价格层尚未建模） | — |

**根因**：v2_plan 是 Xboard 原生表（`套餐/plan` 语义），被我们塞进了「上游接入 + 资费 + 展示」三层职责，**没有任何一层能独立演进**。

## 2. 目标模型（三层独立）

```text
   ┌───────────────────────┐   ┌───────────────────────┐   ┌───────────────────────┐
   │ ① 上游接入层 (Upstream)│   │ ② 资费层 (Pricing)     │   │ ③ 商品展示层 (Listing) │
   │  - 上游身份            │   │  - SKU (KC 视图)       │   │  - 卡片配置            │
   │  - 上游目录            │   │  - 周期价规则          │   │  - 类型标 / 优惠行      │
   │  - 套餐键映射          │   │  - 充值包价            │   │  - 可见 / 可售          │
   │  - 健康度              │   │  - 权益价规则          │   │  - 上游健康展示门控     │
   └──────────┬────────────┘   └──────────┬────────────┘   └──────────┬────────────┘
              │ 引用 upstream_plan_key     │ 引用 plan_id                │ 引用 plan_id
              └────────────────────────────┴──────────────────────────────┘
                                                          │
                                                          ▼
                                                    前台商品页
```

**三层只通过 ID 引用，无字段冗余**；换上游不影响资费、不动卡片；调价不动卡片与上游；换皮不动上游与资费。

## 3. 数据模型调整

> 新表全部建在 KC 数据库（`plus_papay`），命名沿用 `kc_*` 约定；通过 `kc_*` 与插件 / 前台解耦。

### 3.1 上游接入层

```sql
-- 上游身份（KC 侧"我在对接哪个供应商"）
kc_upstreams
  id PK
  code UNIQUE          -- 'zovo' / 'mock_zovo' / 未来 'epay'
  display_name         -- 后台显示名
  protocol ENUM        -- 'mock' / 'rest' / 扩展
  status ENUM          -- 'active' / 'paused' / 'archived'
  base_url             -- 可空（mock 不需要）
  api_key_ref          -- 引用密钥名（实际密钥放 .env，不入库）
  config_json          -- 上游特有配置（超时、重试...）
  created_at / updated_at

-- 上游套餐目录（"上游卖什么"）
kc_upstream_plans
  id PK
  upstream_code FK → kc_upstreams.code
  upstream_plan_key    -- 'plus' / 'pro_5x' / 'credit500'...
  display_name
  sku_type ENUM        -- 'subscription' / 'topup' / 'credit'
  period ENUM          -- 'month' / 'quarter' / 'year' / 'once'
  upstream_price_cents -- 上游报价（仅参考，不直接展示）
  currency CHAR(3)     -- 'USD'
  enabled BOOLEAN
  UNIQUE(upstream_code, upstream_plan_key)
```

**健康度**（现状 `supplier-health.js`）保持不变，但展示门控改为**对 upstream** 聚合（多 plan 共享），数据存 KC 表 `kc_upstream_health_snapshots`（与 supplier-health 字段兼容）。

### 3.2 资费层

```sql
-- KC 视图 SKU（与 v2_plan 解耦的"我们的商品 SKU"）
kc_plans
  id PK
  code UNIQUE          -- 'plus_m' / 'plus_y' / 'topup_500'...
  upstream_plan_key FK -- → kc_upstream_plans.upstream_plan_key（按 upstream_code 区分；多供应商见 §10）
  kc_type ENUM         -- 'recharge' / 'account' / 'entitlement'（与商品类型体系 v1.0.0 一致）
  display_name
  status ENUM          -- 'active' / 'paused' / 'archived'

-- 资费规则（"我们卖多少钱"——核心是规则，不是字段）
kc_pricing_rules
  id PK
  plan_id FK → kc_plans.id
  source ENUM          -- 'manual'（运营手工）/ 'promotion'（促销期）/ 'entitlement'（权益价占位）
  period ENUM          -- 同上游语义；'once' 表示充值包/单次
  amount_cents         -- 售价（按"分"计，与 Xboard v2_plan 一致；展示层美元显示守护不受影响）
  priority int         -- 多规则叠加时的优先级（如权益价 priority 高于 manual）
  valid_from DATETIME  -- 可空（限时促销）
  valid_until DATETIME -- 可空
  enabled BOOLEAN
  note VARCHAR(200)    -- 备注

-- 价格引擎快照（订单写入时固化"按当时规则算出多少钱"）
kc_order_pricing_snapshot
  order_id
  plan_id
  base_price_cents       -- 标价（manual 价）
  applied_source ENUM    -- 命中的 source
  applied_rule_id FK
  final_price_cents      -- 实际收
  entitlement_grant_id   -- 若权益价，记 grant 引用（可回补次数）
  snapshot_json          -- 当时命中的规则全集（含未命中）
  created_at
```

> **关键约定**：售价字段名 `amount_cents`、货币 `USD`、单位"分"——保持与 `v2_plan.month_price` 一致；展示层照常经"货币守护"渲染为 `$`。

### 3.3 商品展示层

```sql
-- 卡片配置（从 v2_plan.kc_card 拆出，沉淀成独立表）
kc_listing_cards
  plan_id FK PK         -- 一 plan 一卡
  -- 字段沿用现有 cardNorm 白名单：title, subtitle, badge, type, features, guarantees, tip, button, chips...
  card_json JSON        -- 整个 card 配置对象（与现有 cardParse 兼容）
  is_visible BOOLEAN    -- 后台开关
  listing_state ENUM    -- 'onsale' / 'featured' / 'soon' / 'soldout' / 'manual'
  sort INT
  updated_at
```

> 卡片表独立后，`v2_plan.kc_card` 字段**仅作读迁移兼容**（老路径继续能读）；新写入路径统一走 `kc_listing_cards`。

### 3.4 权益层（接 §5 触发场景）

```sql
kc_entitlements                    -- 权益规则（"一种权益"）
  id PK
  code UNIQUE
  display_name
  description
  status ENUM                      -- 'draft' / 'active' / 'paused' / 'archived'
  duration_days INT                -- 有效期（开权益后 N 天内有效）；0 = 永久
  total_uses_per_grant INT         -- 单份可用次数；0 = 不限
  per_period_limit INT             -- 0 = 不限
  per_user_limit INT               -- 0 = 不限
  valid_from / valid_until DATETIME
  created_at

kc_entitlement_targets             -- 权益适用 plan（多对多）
  entitlement_id FK
  plan_id FK
  benefit_type ENUM                -- 'price_discount' / 'price_override' / 'action_switch'（§10 拍板）
  benefit_cents                    -- 折扣/直减金额（分）；权益价 = max(标价 - benefit_cents, 0)
  PRORULE(CK benefit_cents >= 0)
  PK(entitlement_id, plan_id)

kc_entitlement_grants              -- 用户持有的权益（"已开通"）
  id PK
  user_id                          -- Xboard 通行 user id
  entitlement_id FK
  source_order_id                  -- 来源订单（开通权益时）
  expires_at DATETIME              -- NULL = 永久
  remaining_uses INT               -- 剩余次数
  status ENUM                      -- 'active' / 'expired' / 'revoked'
  created_at / updated_at

kc_entitlement_uses               -- 使用记录（用于回补 + 审计）
  id PK
  grant_id FK
  order_id
  plan_id
  rule_id FK                       -- kc_pricing_rules.id（权益价规则占位）
  amount_saved_cents
  created_at
```

**索引**：`(user_id, status)`（前台"我的权益"查询）；`(entitlement_id, status)`；`kc_entitlement_targets.plan_id`（价格引擎反查）。

## 5. 权益触发资费切换（核心场景设计）

### 5.1 业务流程

```text
T0  运营配置权益「Plus 季卡 8 折」：
       kc_entitlements row（status=active, duration=30, total_uses=2）
       kc_entitlement_targets row（plan_id=plus_q, benefit_cents=3000）

T1  客户在商品页点开「Plus 季卡 8 折」权益商品：
       - 卡面金色「权益」标
       - 价 = 权益商品自身标价（与权益价不同：这是"花多少钱买权益资格"）

T2  客户付款购买权益商品：
       - order/save（amount = 权益商品标价）→ payment.notify.verified → COMPLETED
       - 履约钩子 order.open.after（新增）调 KC 接口 `/api/admin/entitlements/{id}/grant`：
            INSERT kc_entitlement_grants (user, entitlement, expires_at=now+30d, remaining=2, status=active)

T3  客户去下"Plus 季卡"代充商品（受权益影响的 plan）：
       - 卡面自动加"权益价 $X（原 $Y）" + "权益已生效"小标
       - 用户点"立即购买" → 弹窗金额行 "权益价 $X（原 $Y，剩 2 次 / 30 天到期）"
       - 提交订单 → 调用 pricing/quote：
            base = manual rule (e.g. 12000 cents)
            candidates = entitlement grant's target rule (priority 高)
            final = min by benefit_cents → 9000 cents
            breakdown 包含 grant_id，提示运营/客服"该订单用了哪份权益"
       - 订单落 kc_order_pricing_snapshot；状态进入支付

T5  订单成功（payment.notify.verified）：
       - 减少 grant.remaining_uses（仅当 benefit_type=price 时）
       - 写 kc_entitlement_uses
       - 若 uses 归零 → grant.status='expired'（保留审计行）

T6  退款 / 失败回补：
       - 订单 COMPLETED→REFUNDED → entitlement_uses 标记无效 → 回补 grant.remaining_uses
       - 退款时权益价 = 0（退还实付金额），不二次算权益
```

### 5.2 关键设计点

- **自动取最优**：多权益重叠时，price engine 取 `min(final_cents)`（最低实付），不叠加（明示）。若未来需要叠加，再开 `accumulation_strategy`。
- **前置可见**：权益价在卡面与弹窗**两处可见**（不止结算页）；前端拿 pricing/quote 渲染。
- **不破坏价格不变性**：权益价订单在 `kc_order_pricing_snapshot` 留底，退款按 snapshot 金额退（不二次算）。
- **使用次数与有效期**：过期 / 归零时 grant 失效；前台自动隐藏相关 plan 的权益价；不删 grant 留审计。

### 5.3 退货与争议

- **权益商品本身**：开通后不可退（与《商品类型体系 v1.0.0》§5.4 一致；购前明示）。
- **被权益价命中的订单**：退款按 snapshot 金额退；如该 grant 已扣次数，回补；如 grant 已过期，回补失败时记 audit（运营后续处理）。
- **权益被撤销（人工）**：未下单的 grant 标 `revoked`、前端立即隐藏权益价；已下单未支付的不再重新计价；已支付订单权益价不回退（业务发生时点决定）。

### 5.4 后续扩展（不在本方案 MVP）

- **动作型权益**（`benefit_type=action_switch`）：客户买权益后自动执行某动作（如自动将他订阅从 A 档切到 B 档）。
- **权益互通**（多权益叠加规则）：当前默认取最优；未来可加 `accumulation_strategy`。

## 8. 风险与红线

| 风险 | 对策 |

## 9. 分期路线（建议；每段停下确认）

> 当前基线 v1.14.0；本方案落地预计跨多个版本。本节是路线图而非版本号。

| 期 | 目标 | 关键产出 | 停条件 |
|---|---|---|---|
| **R1 · 上游接入层** | 三层中先把"上游"独立；后台新增"上游接入"页 | kc_upstreams / kc_upstream_plans 表与接口；M1/M2 迁移；后台页可用 | 至少 1 个 SKU 切换上游不影响前台展示 |
| **R2 · 资费层** | 资费与展示解耦；后台新增"商品 SKU + 资费配置"页 | kc_plans / kc_pricing_rules 表与接口；pricing/quote MVP（仅 manual 价）；插件改走 quote | 手动调价生效、无副作用 |
| **R3 · 展示层独立** | 卡片从 v2_plan 拆出；新"商品卡片"页替代旧页（双轨） | kc_listing_cards 表；老字段读路径保留 | 三页齐跑、迁移比对一致 |
| **R4 · 权益 MVP（价格型）** | 用户买权益 → 下单价自动按权益价 | kc_entitlements* 表；定价引擎权益分支；"我的权益"用户页；触发场景走通 | 端到端：开权益 → 下单价按权益 → 退款回补 |
| **R5 · 权益高级与审计** | 撤销、人工冻结、过期提醒、审计导出 | 后台运营动作；客服台查询 | 红线审计通过 |
| **R6 · 动作型权益**（可选） | 客户买权益自动执行某动作（如自动换订阅） | benefit_type=action_switch | 与 R4 解耦、可独立排期 |
| **R7 · 老字段下掉** | v2_plan.kc_card / plugins.config.packages 移除 | 迁移稳定 ≥ 1 个小版本后 | 全量数据一致性比对通过 |

> 每期内仍走开发规范六步：版本号→代码→同步全景→自测→CHANGELOG→入口；产出独立版本号（v1.15.x 起）。

## 10. 待拍板（审核要点）

1. **三层粒度**：三独立表全拆（推荐）or 部分独立表 + 部分配置 JSON？推荐前者（解耦彻底、迁移代价一次性）。
2. **权益触发的"切换"类型 —— 价格切换（推荐 MVP）or 动作切换（如自动换订阅）？** 推荐前者（与商品类型体系 v1.0.0 §5 一致；后者 R6 再做）。
3. **权益是否作用储值型商品（充值包）？** 红线相关 —— 充值包定价原本是面值（如 $500 充 $500 到余额），打权益价等于变相"折价卖余额"。建议 **MVP 禁止权益作用于 topup**，由后台校验。
4. **多供应商**：一个 plan 允许多个 upstream（如 Zovo 断 / 自动切 epay）？建议 **MVP 不做**，单 upstream；规划 R7+ 评估。
5. **价格引擎权限**：quote 接口谁可调？建议：插件服务端代理（BFF 模式，与运营台契约 §3 一致）；浏览器不直连。
6. **页面入口**：运营壳菜单新增三项「上游接入 / 商品 SKU / 权益」是否合适？现有入口「商品卡片配置」是否要并入「商品 SKU」？
