# API 客户自助门户设计方案 v1.0.0

> **方案编号**：`SP-2026-10-13-PORTAL-v1.0.0`　**状态**：待评审（只出方案，不执行开发）
> **上游依赖**：`v1.25.0 对外分销 API`（接口与客户体系已上线）
> **一句话**：给下游接入方一个**自助门户**（登录后看凭证/文档/订单/余额），运营在后台**一个开关**控制门户开放；信息开放以"客户能自助完成对接"为下限、以"商业机密与系统安全"为红线。

---

## 一、目标与定位

| 问题 | 答案 |
|---|---|
| 这是什么？ | 面向**下游 API 客户**的自助门户（Developer Portal），客户登录后自助完成对接与对账 |
| 给谁用？ | 向你要 API Key 的分销商/接入方（"接接口的客户"） |
| 和运营后台什么关系？ | **完全隔离**：门户只暴露"本客户自己的数据"；运营能力仍在 KC 后台 `/admin` |
| 和商城什么关系？ | 无关：门户不卖货给 C 端，只服务 B 端接入方 |
| 入口在哪？ | `http://<域名>:3100/api-portal`（独立路径，独立登录态） |

**运营价值**：客户自己能看凭证/查订单/对余额 → 少 80% 的"我的 key 呢/这单成功没/还有多少钱"工单。

---

## 二、总体架构

```
┌─────────────────────┐         ┌──────────────────────┐
│  API 客户自助门户     │  登录    │  KC 服务端            │
│  /api-portal        │ ───────> │  /api/portal/*       │
│  · 概览              │ key+secret│  · portal token 签发  │
│  · API 凭证          │          │  · 仅返回本客户数据    │
│  · 接入文档          │ <─────── │  · 开关校验（门户/客户）│
│  · 我的订单          │  数据     └────────┬─────────────┘
│  · 余额与消费        │                    │ 同一套 kc_api_* 表
└─────────────────────┘                    │（客户数据本就隔离）
                              ┌─────────────┴──────────┐
                              │  KC 后台 /admin         │
                              │  「API 客户」页：        │
                              │   · 门户总开关 ← 你要求的 │
                              │   · 客户启停/充值/密钥    │
                              └────────────────────────┘
```

**登录态**：`POST /api/portal/login {api_key, api_secret}` → 签发 portal token（HMAC 签名、含 client_id、24 小时有效）→ 前端 localStorage 持有；**所有门户接口从 token 解出 client_id，禁止请求传 client_id**（隔离的根）。

## 三、信息开放设计（核心：开放什么 / 不开放什么）

### 3.1 开放信息总表

| 页面 | 开放的信息 | 为什么给 |
|---|---|---|
| **概览** | 客户名称/编号、账户状态、**当前余额**、今日/本月调用次数与订单数、消费金额、接入状态检查清单（凭证✓ 文档✓ 首单✓） | 客户进门第一眼：我是谁、还能花多少、用得怎么样 |
| **API 凭证** | API Key（明文可复制）、Secret（**掩码显示**，可"重置"——重置后旧密钥立即失效、新密钥一次性展示）、Base URL、签名规则速查 + 一段可复制的签名示例代码 | 客户自助取用/轮换密钥，不用翻邮件找初始凭证 |
| **接入文档** | 快速开始、4 个接口的参数/响应示例、签名详解（Node/Python/PHP/curl 四种示例）、错误码表、限流说明、报价锁价规则说明 | 客户自助对接，把"怎么用"一次性说清 |
| **我的订单** | 本客户订单列表：下单时间、**下游单号**、商品名、数量、**金额**、状态（delivered/failed）、**卡密**（已交付可查看/复制）、内部单号（order_id） | 交付物自查 + 对账依据；卡密是客户买的东西，必须给 |
| **余额与消费** | 当前余额、**充值记录**（时间/金额/操作人）、**消费明细**（每笔订单扣费，可关联订单） | 对账闭环：钱从哪来、花到哪去 |
| （后续）用量报表 | 按天/接口的成功率、错误码分布、P95 延迟 | 客户排障；本期并入概览的简版计数 |

### 3.2 安全边界——**明确不开放**（红线）

| 不开放 | 原因 |
|---|---|
| **成本价 / 加价率 / 利润率** | 商业机密；客户只需知道自己付多少钱 |
| **上游供应商身份与接口**（ZovoCard 等、"上游套餐键"如 `plus`） | 客户不该知道货源是谁；商品以 SKU 与商品名呈现（如 `xplan_1 / ChatGPT Plus 一个月`） |
| 其他客户的任何信息 | 数据隔离 |
| 运营后台功能入口 | 门户与 `/admin` 登录态、路由、鉴权三者独立 |
| 平台内部运维数据（任务日志、卡池、会话池等） | 与客户无关 |
| 修改本客户的加价率/限额（自助） | 商务变更走运营；客户只能"看"和"申请" |

> 一个原则：**客户能看到"自己付了多少钱、买了什么、怎么调用"，看不到"你的货从哪来、你赚多少"**。

## 四、页面与菜单设计（前端菜单结构）

门户为独立 SPA，左侧菜单（即你要的"API 菜单"）：

```
┌──────────────────┐
│  KC API 门户      │   ← 品牌区（可配置名称）
├──────────────────┤
│ ▸ 概览            │  ← 默认落地页
│ ▸ API 凭证        │
│ ▸ 接入文档        │
│ ▸ 我的订单        │
│ ▸ 余额与消费      │
├──────────────────┤
│ 客户名 / 退出登录  │
└──────────────────┘
```

**① 概览**：余额大数字卡；今日/本月调用与订单四宫格；"接入三步骤"检查清单（已完成打勾，未完成引导去对应页）；门户公告位（维护通知）。

**② API 凭证**：
- Base URL（复制）
- API Key（明文 + 复制）
- Secret（`••••••••` + 「显示/隐藏」切换 + 「重置」按钮——重置需二次确认，成功后弹窗**一次性展示**新 Secret）
- 签名速查卡：规则一行 + 「复制示例代码」（Node/Python/curl 三 Tab）

**③ 接入文档**：纯静态内容页（MD 渲染或预设 HTML），含：5 分钟快速开始、接口列表（catalog/quote/orders/查单，参数表 + 请求/响应 JSON 示例）、签名详解、错误码表（`INVALID_SIGNATURE / TIMESTAMP_EXPIRED / QUOTE_EXPIRED / PRICE_CHANGED / INSUFFICIENT_BALANCE / SKU_UNAVAILABLE / RATE_LIMITED / CLIENT_DISABLED`）、限流与锁价规则。

**④ 我的订单**：表格（时间 / 下游单号 / 商品 / 数量 / 金额 / 状态 / 卡密）+ 筛选（近 7/30 天、全部/成功/失败）+ 卡密列「复制」按钮。

**⑤ 余额与消费**：余额卡 + 两个 Tab：充值记录（时间/金额/备注）/ 消费明细（时间/订单/金额）+ 底部固定文案："充值请联系运营（或在运营后台申请）"——**MVP 不做自助充值**（打款对账必须人工）。

## 五、后端开关设计（你要求的"能在后端控制开关"）

**三级开关，前两级本期做，第三级预留**：

| 级 | 开关 | 控制对象 | 实现 |
|---|---|---|---|
| L1 | **门户总开关** | 整个门户开放/维护中 | KC 后台「API 客户」页顶部 Switch；存 `app_config.api_portal_enabled`；**关闭时门户登录页显示"维护中"**，已登录用户下次请求被拒（403 PORTAL_DISABLED） |
| L2 | **客户级开关** | 单个客户能否登录 | 复用 `kc_api_clients.status`（active/disabled）；停用客户登录即拒（403 CLIENT_DISABLED） |
| L3 | 菜单项开关 | 门户内某个菜单显隐（如临时关"我的订单"） | 预留：门户菜单配置存 `app_config.api_portal_menu`（JSON）；本期不做 UI |

> L1 开关是运营的"急停按钮"：门户出问题一键关闭，不影响已在下游代码里的 API 调用（**门户与 API 服务互不影响**——这是有意的设计）。

## 六、接口清单（新增 `/api/portal/*`）

| 接口 | 说明 |
|---|---|
| `POST /api/portal/login` | `{api_key, api_secret}` → `{portal_token, client:{name,code,status}}`；校验 L1/L2 开关 |
| `GET /api/portal/me` | 客户信息 + 余额 + 今日/本月调用与订单统计 + 接入清单状态 |
| `POST /api/portal/credentials/reset-secret` | 重置 Secret（返回一次性新值，旧值立即失效） |
| `GET /api/portal/orders?range=30d&status=all&page=1` | 本客户订单（**SQL 强制 client_id 条件**），卡密仅 delivered 返回 |
| `GET /api/portal/billing` | 余额 + 充值记录 + 消费明细（同一聚合） |

**与开放 API 的隔离**：`/api/open/v1/*`（下游程序调）与 `/api/portal/*`（下游人调）**鉴权体系完全独立**（前者 Key+签名、后者 portal token），互不继承权限。

## 七、技术方案要点

1. **页面**：`public/api-portal.html`（原生 JS SPA，与 admin.html 同技术栈，无新依赖）；路由 `/api-portal`（server.js 放行，同 `/admin` 模式）
2. **token**：`HMAC-SHA256(secret_env, payload)` 自签（不落库，24h），payload = `{cid, iat, exp}`；密钥存 `.env`（`PORTAL_TOKEN_SECRET`）
3. **隔离**：portal 中间件统一解 token → `req.portalClient`；所有 SQL 强制 `client_id = req.portalClient.id`；**不接受任何客户端传入的 client_id**
4. **数据来源**：全部读 v1.25.0 已有三表（`kc_api_clients / kc_api_orders / kc_api_quote_logs`），零新表
5. **部署**：随 KC 服务（3100）；正式开放前需域名反代 + HTTPS（门户走公网，密钥登录必须 TLS——列入上线前置）
6. **安全细节**：登录失败不提示"key 错还是 secret 错"（统一"凭证无效"）；登录限流（同 IP 10 次/分钟）；Secret 重置后**旧 portal token 不失效但旧 API secret 立即失效**（文档明示）

## 九、本方案已做出的决策（无需再选）

1. **独立门户**（`/api-portal`）而非塞进商城或运营后台——身份与数据模型不同，混排会污染两侧
2. **登录 = API Key + Secret**（零新概念）；门户独立密码后续版再加
3. **Secret 门户内掩码 + 可重置**，不明文常展（降低泄露面）
4. **成本/加价率/上游身份绝不上面**（红线，见 §3.2）
5. **MVP 不做自助充值**（打款对账必须人工；门户只展示余额与记录）
6. **门户开关与 API 服务解耦**（关门户不影响下游程序调用）
7. 菜单默认五项：概览 / API 凭证 / 接入文档 / 我的订单 / 余额与消费
