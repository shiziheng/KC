# 开发规范（KC-PAY-GPT）

> **本文件是开发的强制规范。**任何模型或开发者在动手改代码前必须先读完本文件。
>
> 配套文件：`docs/产品全景.md`（产品能力与边界唯一正本）、`CHANGELOG.md`（版本记录正本，**只追加不覆写**）、`README.md` 顶部「开发协作入口」。

## 0. 强制阅读顺序（最重要）

无论你是哪个模型、哪次会话，**开工前必须按此顺序读取，缺一不可**：

| 顺序 | 文件 | 作用 | 必读 |
|---|---|---|---|
| 1 | `README.md` 顶部「开发协作入口」段 | 拿到最新版本号、当前进度、下一步 | ✅ 必读 |
| 2 | `docs/产品全景.md` | **系统有什么功能、用户怎么用、未来做什么** | ✅ 必读 |
| 3 | `CHANGELOG.md` **只看顶部第一个版本条目** | 知道最近做了什么、为什么这么做 | ✅ 必读 |
| 4 | `docs/00_项目状态.md` | 运行环境、部署、待办、关键文件索引 | ✅ 必读 |
| 5 | 本文件 `docs/开发规范.md` | 动手前的规则 | ✅ 必读 |
| 6 | `.workbuddy/memory/MEMORY.md` | 长期坑与不可变约束 | 建议读 |

**两个关键约定：**

1. **`docs/产品全景.md` 是产品能力与边界的唯一正本。**散落的 FEAT/ARC/S0～S13 文档与它冲突时，**以它为准**，并修正散落文档。
2. **`CHANGELOG.md` 的第一个版本条目永远是最新的。**不需要搜索、不需要翻历史，直接读顶部即可。

## 1. 版本号规则（语义化版本）

格式：`v主版本.次版本.修订号`，例：`v1.1.0`

| 改动类型 | 版本号变化 | 例子 |
|---|---|---|
| 新增功能 | 次版本 +1 | `v1.0.0` → `v1.1.0` |
| 修 bug / 小调整 | 修订号 +1 | `v1.1.0` → `v1.1.1` |
| 架构重写 / 不兼容改动 | 主版本 +1 | `v1.9.9` → `v2.0.0` |
| 仅文档、不动代码 | 不升版本，在文件头记「文档修订日期」 | — |

**迭代粒度：一个有明确目标的开发批次 = 一个版本。**
- ✅ 算一个版本：「一键部署脚本 + 部署说明」「独立后台基础架构」「修复兑卡并发超发」
- ❌ 不算版本：修一个错别字、调一次格式

## 2. 每次迭代的强制流程

**六步，一步都不能省：**

```
① 定版本号 → ② 改代码 → ③ 同步产品全景 → ④ 自测验证 → ⑤ 写 CHANGELOG → ⑥ 更新入口文件
```

### ① 定版本号
开工前先算出下一个版本号，**并在动手前告诉用户**。例：`v1.2.0（新增：独立前台支付页）`

### ② 改代码
遵守第 3 节「不可变约束」和第 5 节「代码约定」。

### ③ 同步产品全景（涉及功能时必做）
如果本次改动**新增、删除或改变了用户能感知的能力**，必须同步更新 `docs/产品全景.md`：
- 新功能 → 补进对应角色的功能表，状态标「已上线」，并在行尾加 `<!-- feat:xxx -->` 标记
- 删功能 → 从功能表移除，并记进「明确不做什么」
- 改流程 → 更新第二节的流程图
- 改优先级或规划 → 更新第五节三档规划
- **同时把产品全景顶部的「对应版本」改成新版本号**（这是滞后检测的依据，忘了改会被自检拦下）

> 只改代码不改全景 = 未完成。**全景文档是产品能力的唯一正本**，漏改会让下一任接手者误判系统现状。

### ④ 自测验证
每个版本必须有验证记录，写清**跑了什么、结果如何**。禁止「应该没问题」这类无验证交付。
- Node 代码：`node --check` 语法检查
- 脚本：实际执行并贴出关键输出
- 数据库改动：写清影响的表和是否可逆
- **改完前端注入脚本必须 `node --check`**，且必须重新部署验证

### ⑤ 写 CHANGELOG（最重要）
在 `CHANGELOG.md` **顶部**插入新版本条目，**不要动下方任何历史内容**。每条必须含「验证」和「下一步」。

### ⑥ 更新入口文件
同步更新 `README.md` 顶部的「最新版本」和「当前进度」，`VERSION.json` 的版本号，以及 `docs/00_项目状态.md` 的执行状态。

## 3. 不可变约束（违反即为严重错误）

这些是产品级红线，**任何迭代都不得放宽**：

1. **ZovoCard 持续 Mock** —— `ZOVOCARD_MOCK=1` + `REQUIRE_ZOVOCARD_MOCK=1` 必须保持开启，普通后台不得提供关闭开关。
2. **Session 永不落库** —— 不保存 Session / access_token / refresh_token / Cookie / 密码 / 卡号 / CVC。只允许脱敏账户摘要和短时 `credential_ref` 哈希。**任何新 API、队列、日志、审计都不得恢复凭据落库。**
3. **真实支付/履约/外部 API 保持关闭** —— 未经用户明确批准不得开启。
4. **KC 后台及技术菜单保持原样** —— 不因业务需要改动 KC 菜单结构。
5. **资金由不可变流水驱动** —— 支付、钱包、履约、补偿、售后状态分离；余额变动必须有唯一 `event_key` 幂等流水。
6. **并发抢占用 `INSERT IGNORE`** —— 绝不用 `ON DUPLICATE KEY UPDATE`（mysql2 下 affectedRows 仍返 1，会超发）。
7. **`.env` 不写进任何文档** —— 凭据、密钥、密码一律不进文档、代码注释、CHANGELOG。

## 4. 协作节奏

- **先方案 → 再计划 → 分段执行；每段停下等用户确认。** 不允许连续做多个阶段不汇报。
- 每个阶段完成后明确告诉用户「做完了什么、下一步做什么」，等确认再继续。
- 用户看不懂技术术语时，**用业务语言描述**：「谁在用 → 做什么动作 → 应该看到什么」，不要用接口名、字段名、状态码堆砌。
- 发现方案有问题，**直接说，不要默默照做**。

## 5. 代码约定

| 项 | 约定 |
|---|---|
| 文件名 | **全英文**，不用中文/emoji/特殊字符（Windows 编码坑 + 跨平台兼容） |
| 目录结构 | 见 `docs/01_目录结构.md`，新增目录先更新该文件 |
| 数据库表 | 独立业务表统一 `biz_` 前缀；**只新建表，不改 KC/Xboard 旧表** |
| 迁移脚本 | `business-infra/db/migrations/` 下编号递增；`down` SQL 仅人工评审，禁止启动时自动执行 |
| 前端注入 | 三份源文件在 `tools/kc_*_inject.html`；注入脚本只取 `<script>` 内内容 |
| 注释语言 | 中文注释，**不加废话注释**，只写「为什么这么写」 |

## 6. 文档同步闸门（不靠自觉，靠硬拦截）

### 怎么用

```bash
node tools/check-docs-sync.js          # 人读输出
node tools/check-docs-sync.js --json   # 机器可读（CI 用）
npm run docs:check                     # 等价 npm 脚本
```

### 什么时候会被拦

已配置 `git config core.hooksPath .githooks`，**pre-commit 钩子会自动跑自检**。以下情况**提交会被直接拒绝**：

| 情况 | 说明 |
|---|---|
| 产品全景版本落后 | 全景「对应版本」低于当前版本 → 新增功能很可能没同步 |
| 三处版本号不一致 | `VERSION.json` / `CHANGELOG.md` / `README.md` |
| 产品全景章节缺失 | 六大章节被改名或删除 |
| 未来规划三档被混 | 远期想法混进「待做」，或「明确不做」消失 |
| 产品红线被删 | Mock 锁、Session 不落库等红线条目不见了 |
| 规范丢了同步步骤 | 开发规范里的「同步产品全景」步骤被删 |
| 版本条目缺验证/下一步 | CHANGELOG 条目不完整 |
| 编码损坏 | 关键文件含 U+FFFD 乱码 |
| 入口未引用产品全景 | 模型将找不到产品正本 |

### 紧急绕过

纯文案修正等特殊情况可临时跳过：`git commit --no-verify`。**不要常态化使用**，否则闸门就失效了。

### 为什么这样设计

「改了功能忘更新文档」是**看不见的腐化**——没有报错、没有异常，只有接手的人默默按过期信息干活。因此必须做成**提交即拦截**，而不是写在规范里靠自觉。

## 7. 部署与验证

- **一键脚本服务清单的唯一来源是 `deploy-manifest.json`** —— 新增/删除/改名服务只改这个文件，Windows 与 Linux 两套引擎自动跟随。
- 改完部署相关必须跑 `verify` 自检：`.\kc-deploy_20261007.ps1 verify` / `./kc-deploy_20261007.sh verify`
- Xboard 改配置后**必须 `php artisan optimize:clear`**，否则跑旧脚本。
- **本机环境坑**（最易浪费时间，改代码前务必知道）：本机 Bash 没有 coreutils（`ls`/`cat`/`sleep` 等不可用），一律写 `.js` 用 node 跑；`docker` 不在 PATH 需用全路径。详细见 `.workbuddy/memory/MEMORY.md`。
- ⚠️ **不要在有未提交新文件的工作区跑 `git reset --hard`** —— 会连新文件一起删掉。提交前先 `git status` 确认。

## 8. CHANGELOG 写作模板

每个新版本条目严格按此结构：

```markdown
## v1.2.0 · 2026-10-08 · 新增独立前台支付页

**一句话概括**：用户在独立前台可以直接用 USDT 支付并看到实时到账状态。

### 新增
- `web/app/recharge/page.tsx` —— 独立充值页，金额档位 + 随机收款码

### 修改
- `business/orders.js` —— 订单查询补 `pay_status` 字段

### 修复
- 兑卡并发超发：`INSERT IGNORE` 替代 ODKU，8 并发只产 1 张卡

### 验证
- `node --check` 通过；Vitest 14/14；HTTP 200 实测

### 影响与风险
- 需要重建 app 容器；未开启真实支付，仍为 Mock

### 下一步
- 灰度验证真实小额首单
```

**每条必须包含「验证」和「下一步」** —— 没有验证记录和下一步的版本条目视为未完成。
