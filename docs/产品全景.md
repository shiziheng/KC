## 一、这个系统是做什么的

KC-PAY-GPT 是一个 **ChatGPT Plus / Pro 自动代充平台**。当前独立业务前台和后台只开放 Mock 流程：可以配置商品、创建订单、模拟支付/履约、查看凭证和处理售后；不收真实款、不扣余额、不调用真实上游。

**系统由五个部分组成**。独立业务后台 R0–R4 与独立 Next.js 前台已统一部署；用户订单、运营收尾仍只在 Mock 模式运行：

| 部分 | 用什么技术 | 干什么 | 用户看得见吗 |
|---|---|---|---|
| **KC 代充引擎** | Node.js + 浏览器自动化 | 真正去开通订阅的核心引擎 | 否；当前新前台不调用 |
| **独立代充前台** | Next.js | 商品浏览、用户 Mock 订单、状态和交易凭证 | 是；Mock 模式 |
| **Xboard 商城**（过渡/回退） | PHP + Laravel | 保留旧商品、订单和收款能力供旧流程回退 | 是；与新业务订单隔离 |
| **BEpusdt 收款网关** | Go + SQLite | 旧流程的 USDT 网关；新前台不调用 | 仅旧流程使用；新前台不开放真实收款 |
| **独立业务后台** | Node.js + Express | 给运营/客服/财务配置商品、查单、处理异常/售后 | 否；内部人员用，保持 Mock |

> **新独立前台与旧 Xboard 商城是两条隔离路径。**新前台只跑 Mock，不替换旧商城，也不做数据迁移或灰度切换。Xboard 继续作为旧流程回退入口；KC `/admin` 技术菜单不改。

## 二、系统怎么向用户卖东西（核心业务流程）

### 当前可用流程：用户体验一笔 Mock 代充订单

```text
1. 用户登录独立前台，浏览运营后台上架的 Plus / Pro 商品
        ↓
2. 用户选择商品并创建订单；订单归属当前登录用户
        ↓
3. 订单显示「待模拟支付」；用户可手动推进模拟支付状态
        ↓
4. 用户可继续推进模拟履约状态，或提交售后留言
        ↓
5. 用户查看/打印订单状态凭证

以上动作只写独立业务库，不扣款、不收款、不调用 ZovoCard 或其他上游。
```

### 用户会看到什么状态（Mock）

| 状态 | 什么意思 |
|---|---|
| 待模拟支付 | 订单已创建，尚未模拟确认 |
| 模拟已支付 | 只表示演示状态变更，不代表收到款项 |
| 待模拟处理 | 等待用户推进 Mock 履约 |
| 模拟完成 | 演示流程结束，不代表 ChatGPT 权益已开通 |
| 售后待受理/处理中 | 用户留言进入运营队列，等待人工处理 |

**关键规则：模拟状态不是现实交易事实。**支付与履约分别展示；售后决定只写处理记录，不执行退款或余额补偿。

### USDT 充值后台演练

新前台没有真实 USDT 充值入口。后台保留 Mock 随机金额、模拟核验和受控补记演练；它不连接钱包、区块链或 BEpusdt，也不会修改 KC/Xboard 余额。

### 售后服务流程

```text
用户在 Mock 订单页提交问题说明（不得包含账号凭据）
        ↓
运营后台查看留言并记录受理、同意、拒绝或结案决定
        ↓
状态变化只用于流程演示；不会自动退款、补偿或改余额
```

- 本期只纳入 Zovo `product=gpt`：普通商品候选为 `go`、`plus`、`pro_5x`、`pro_20x`、`pro_50x`；Codex 点数加购为 `credit250`、`credit500`、`credit1000`、`credit2500`、`credit5000`、`credit25000`。
- `pro_20x_renew` 是 Pro 20x 续费绑卡，不是当次订阅充值，不纳入普通商品。Claude/Grok 不属于本期 ChatGPT 代充商品。
- Zovo 负责提供上游套餐键/名称、启用与可售标志、点数/订阅要求、服务费和目录版本。实际商品能否保存要求出现在 GPT registry、`purchasable=true` 且 `plans[acc_plan_key].enabled=true`。
- 商品面向用户的名称、售价和成本参考仍由运营配置。GPT 价格会随地区、卡 BIN 和账号状态变化，不能把目录示例金额或服务费当成固定售价/实际成本；真实成交报价须由未来获批的 preflight 流程确定。
- 当前展示和校验使用文档整理的 Mock fixture，不表示 Zovo 实时目录状态。Mock 订单快照保存上游套餐引用、目录版本、服务费、点数资格标记和本地订单号作为 `client_request_id`；`upstream order_ref` 为空、状态为未提交，不会创建 Zovo 订单。

## 六、不可跨越的红线

这些是产品级红线，**任何开发迭代都不得放宽**。详见 [`docs/开发规范.md`](开发规范.md)。

| 红线 | 含义 |
|---|---|
| **代充永远走模拟** | 开发、测试、验收阶段绝不真实调用供应商接口、绝不真实扣钱 |
| **用户授权信息不保存** | 用户粘贴的 ChatGPT Session/token 等账号授权信息不接收、不进数据库、不进日志；Xboard 登录令牌只沿用前台原有登录态，不存入业务库或审计 |
| **真实支付保持关闭** | 真实收款、真实开通、对外接口，在明确批准前全部关闭 |
| **KC 后台菜单不动** | 业务需求不能修改技术后台结构 |
| **钱必须走流水** | 余额不能直接改，每笔变动必须有唯一凭证，能复算 |
| **并发要防超发** | 同一张卡密同时只能被一个人抢到 |
| **密钥不进文档** | 密码、密钥、账号一律不写进任何文档和代码注释 |

| 我想知道 | 看哪个文件 |

| 某次改动验证得怎么样 | `docs/验收/` |
| 历史上为什么这么设计 | `docs/设计/` 对应 FEAT 文档 |

### 维护规则

1. **功能增删改必须同步更新本文件**，并按开发规范升版本、在 CHANGELOG 记一条。
2. **同时把顶部「对应版本」改为新版本号** —— 这是滞后检测的依据，忘了改会被 `tools/check-docs-sync.js` 拦下。
3. **提交前跑一次自检**：`node tools/check-docs-sync.js`（pre-commit 钩子也会自动跑）。
4. **只描述"是什么"，不记录"怎么改的"**（避免和 CHANGELOG 重复）。
5. **写业务语言**：说"用户能看到什么"，不说接口名和字段名；技术细节放到 `docs/接口/`。
6. **"未来规划"三档不能混**：想做、明确不做、远期想法必须分开写，避免把远期想法误读成马上要做。
7. 本文件是**产品能力与边界的唯一正本**。如果散落的 FEAT 文档和本文件冲突，**以本文件为准**，并修正散落文档。
