## 一、这个系统是做什么的

KC-PAY-GPT 是一个 **ChatGPT Plus / Pro 自动代充平台**。

用户付钱（或用平台余额），系统自动帮他在 ChatGPT 官方账号上开通订阅。用户不需要自己操作复杂流程，只需要：选商品 → 提供账号授权信息 → 付款 → 等几分钟。

**目标系统由四个部分组成**。前三项是现有系统组成；独立业务后台仍是已确认的建设目标，当前实现代码缺失，不能视为已上线：

| 部分 | 用什么技术 | 干什么 | 用户看得见吗 |
|---|---|---|---|
| **KC 代充引擎** | Node.js + 浏览器自动化 | 真正去开通订阅的核心引擎 | 否，用户不直接用 |
| **Xboard 商城**（过渡期） | PHP + Laravel | 商品展示、下单、收款的前台 | 是，这是用户现在用的页面 |
| **BEpusdt 收款网关** | Go + SQLite | 收 USDT 加密货币 | 是，用户用它付款 |
| **独立业务后台**（待重建） | 计划采用 Node.js | 给运营/客服/财务用的统一业务后台 | 否，内部人员用；当前未交付 |

> **重要概念：现在用户访问的页面还是 Xboard 商城的页面**，不是我们自己做的。这叫"过渡期"。
> 目标是自己建独立前台和独立后台，让运营人员不用再进 Xboard 那个机场式后台。Xboard 将逐步退出。

## 二、系统怎么向用户卖东西（核心业务流程）

### 主流程：用户买一次代充

```text
1. 用户打开网站，看到代充商品（Plus / Pro 5x / Pro 20x）和价格
        ↓
2. 注册或登录账号
        ↓
3. 选商品 → 点「立即办理」
        ↓
4. 系统引导用户打开 ChatGPT 官网、登录自己的账号，
   然后粘贴一段账号授权信息（我们内部叫 Session）
        ↓
5. 系统先"体检"一下账号：能不能开通、当前有没有订阅
        ↓
6. 用户付款
   ├─ 有余额 → 直接扣余额
   └─ 没余额 → 用 USDT 充值（推荐）→ 余额到账 → 再支付
        ↓
7. 系统自动去 ChatGPT 开通订阅，用户等着就行
        ↓
8. 结果三种：
   ├─ 成功 → 通知用户，订单页显示"已开通"
   ├─ 失败但钱是余额付的 → 自动退回余额
   └─ 失败且钱是 USDT 付的 → 转人工退款
```

### 用户会看到什么状态

| 状态 | 什么意思 |
|---|---|
| 待支付 | 订单已创建，等用户付款 |
| 校验中 | 正在检查账号能不能开通 |
| 代充中 | 正在开通，请耐心等 |
| 已完成 | 开通成功 |
| 失败待处理 | 开通失败，正在自动处理退款 |
| 人工处理中 | 需要工作人员介入，会联系用户 |

**关键规则：付款成功 ≠ 开通成功。** 这是两个独立的状态，页面上会分开显示。用户付了钱但开通失败时，一定会退款或人工介入，不会出现"钱扣了但没开通也没人管"的情况。

### 余额充值流程（USDT）

```text
用户点充值 → 选金额档位 → 系统生成一个专属收款码
（同一个金额会配一个唯一的小数尾数，用来自动认领是哪一笔）
        ↓
用户用 USDT 转入 → 系统自动核对钱包地址、链、金额、时间、确认数
        ↓
全部对上 → 余额入账，订单变已支付
        ↓
对不上 → 转"人工核验"队列，财务用交易哈希核实后受控补单
```

**设计要点**：不是只看金额对不对，必须同时核对钱包地址、链、确认数和交易哈希，防止有人用 1 块钱的转账冒领 100 元的充值。

### 售后服务流程

```text
开通失败或用户不满意 → 用户在订单页申请售后
        ↓
客服受理 → 判断责任 → 退款（余额部分自动退，USDT 部分人工退）
        ↓
售后状态：待受理 → 审核中 → 已同意/已拒绝 → 已处理完成
```

## 四、明确不做什么（防止误判）

这些是**产品决策，任何模型都不能擅自加回来**：

| 不做的事 | 原因 |
|---|---|
| **发票功能** | 开票、红冲、发票管理全部不做。交易凭证不是发票。 |
| **分销提现和推广看板** | 返佣只能进余额，不能提现。不做提现和推广数据看板。 |
| **Xboard 的节点/流量/订阅链接/客户端** | 那是机场功能，和代充业务无关。 |
| **KC 技术后台菜单迁移** | KC 后台保持原样，不迁移、不删除、不重排。 |
| **修改 KC 现有菜单结构** | 业务需求不能动技术后台。 |
| **优惠券和在线客服** | 低优先级，不是当前主线。 |
| **链上钱包自动扫描** | 暂不开发。 |

## 六、不可跨越的红线

这些是产品级红线，**任何开发迭代都不得放宽**。详见 [`docs/开发规范.md`](开发规范.md)。

| 红线 | 含义 |
|---|---|
| **代充永远走模拟** | 开发、测试、验收阶段绝不真实调用供应商接口、绝不真实扣钱 |
| **用户授权信息不保存** | 用户粘贴的账号授权信息，用完即删，不进数据库、不进日志 |
| **真实支付保持关闭** | 真实收款、真实开通、对外接口，在明确批准前全部关闭 |
| **KC 后台菜单不动** | 业务需求不能修改技术后台结构 |
| **钱必须走流水** | 余额不能直接改，每笔变动必须有唯一凭证，能复算 |
| **并发要防超发** | 同一张卡密同时只能被一个人抢到 |
| **密钥不进文档** | 密码、密钥、账号一律不写进任何文档和代码注释 |
