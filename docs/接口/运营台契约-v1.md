## 0. 一页结论

1. **三条原则**：只读优先 / 写操作白名单 / 全程可审计。
2. **不直连数据库**：运营台与各系统之间只走 HTTP 契约；跨系统调用统一由 **Xboard 插件服务端代理**（复用 `KcGateway` 模式），浏览器不直连 KC。
3. **现有资产已够做只读看板**：Xboard 插件 18 条 admin 接口覆盖补偿/流水/风控/售后/充值/客服查询；KC 侧经集成密钥通道提供健康与任务状态；缺口在 §6 列清单（只读优先）。
4. **写操作先过户再上线**：白名单（§3.2）之外不开任何口子；不新增"任意调账"能力，账本（用户/订单/余额/支付）原地不动。

## 1. 适用范围

- **消费方**：自建运营台（路线阶段 2+）；客服工作台（已上线，是本契约的 P1 先例）。
- **提供方**：
  - A. Xboard 插件 API（`admin/kc/*`）——同源，管理员鉴权；
  - B. KC 引擎 API（集成密钥通道 + KC 技术后台通道）；
  - C. BEpusdt 只读对账（待补，见 §6）。
- **路线映射**：阶段 2 = 只读聚合看板；阶段 3 = 写操作按白名单接管；阶段 4 = 商品上架工作台。每阶段开工前单独确认。

## 3. 契约细则

### 3.1 只读接口口径（所有新增只读接口遵循）

- 列表类：**时间范围必选**、分页返回、字段白名单（不透传整行）；
- 详情类：按 ref / 订单号 / 用户标识单条查询；
- 脱敏：Session、密钥、登录凭据不返回；金额以「分」传递、前端统一按 **$** 展示；
- 性能与隔离：单次查询目标 ≤ 2s；**只读接口不参与任何履约链路**（不得成为发卡 / 支付路径的一环）。

### 3.2 写操作白名单（v1 仅以下 8 项，均已有实现）

| 操作 | 接口 | 风险 | 附加要求 |
|---|---|---|---|
| 补偿重查 | compensations/recheck | 低 | — |
| 补偿重试 | compensations/retry | 中 | 沿用现有幂等键 |
| 人工标记完成 | compensations/mark-manual-done | 中 | 二次确认 + 备注 |
| 风控阈值配置 | risk/rules | 中 | 记录变更前后值 |
| 解除临时拦截 | risk/release | 中 | 二次确认 + 原因 |
| 售后处理 | after-sales/process | 中 | 沿用现有审核流 |
| 余额补单记账 | topups/credit | 高 | 二次确认 + 单据引用 + 审计 |
| 标记待复核 | topups/mark-review | 低 | — |

后续批次（阶段 3）拟接入：商品卡片配置（card-config，BFF 代理）、开关与阈值（`app_config` 受控键）——**逐项过白名单流程后才接入**。

### 3.3 鉴权口径

- 同源接口：`['user','admin']`（Sanctum 管理员令牌）；页面壳公开 + token 取同源 localStorage（v1.13.0 先例）。
- 跨系统：浏览器不直连 KC；由插件服务端（`KcGateway` 模式）持集成密钥调用；KC 管理接口不对公网放开。
- 密钥卫生：不进前端、不进日志；轮换流程挂"上线前置"清单。

### 3.4 审计口径

- 写操作四要素留痕：**操作者、时间、对象（ref / 订单号）、结果**；
- 现阶段：写接口已带管理员上下文；运营台 / BFF 接入时统一追加操作日志（不改内核、不动账本）；
- 只读访问同样留痕（BFF 访问日志即可）：查了谁、何时、查了什么。

## 4. 与四后台的关系

运营台 = **日常聚合入口**（看 + 白名单写）；Xboard 原生后台 = 交易内核维护（用户 / 订单 / 余额 / 支付 / 分销）；KC 技术后台 = 引擎与集成；BEpusdt = 收款通道。运营台不替代任何后台，只是把日常动作收在一处。

## 5. 明确不做（写死）

- 不直连任何数据库（尤其写）；不新增任意调账 / 改单能力；
- 不暴露 Session / 密钥 / 敏感凭据；金额不出现非美元符号；
- v1 不做：余额调整、订单状态直接改写、履约人工干预（履约异常一律走补偿队列）；
- 不引入新的支付 / 退款动作（退款仍走既有补偿链路）。
